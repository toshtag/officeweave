### CI の導入時期

CI は P2 では扱わず、P12 完了後の最終工程 F でのみ導入する。

P2 の目的は、開発者が手元で品質を確認できる状態を作ることである。
検証手段が固まる前に CI を組むと、実装途中の暫定的な手順が設定として固定され、
毎 Phase で CI 設定の保守が発生する。

したがって P2 から F までは、すべての検証をローカルで実行する。
F では、その時点で確立した検証コマンドをそのまま CI へ移す。

### 開発制御ツールについて

外部の開発制御ツールは導入しない。

進行状態はロードマップと実行キュー、および Git の履歴で管理する。
1 タスク 1 ブランチ 1 PR を守れば、`git log` と PR 一覧から現在地を復元できるため、
専用ツールを実行環境へ持ち込む必要がない。

以前のロードマップにあった Agent 向け read/write scope の固定タスクも取りやめる。
変更範囲は、実行キューの各タスク定義とブランチ単位の差分で表現する。

## 現在地

現在地は [実行キュー](execution_queue.md) で管理する。
Git の履歴と PR 一覧からも同じ状態を復元できる。

```text
現在の Phase:      P7
直近完了 Task:     P7-T1
次に実行する Task: P7-T2
一度に実行する Task: 1 件
```

## 進行規則

- 1 タスクにつき 1 ブランチ 1 PR とし、独立して検証できる単位まで分解する
- ブランチ名は `p<Phase>/t<連番>-<短い英語>` とする
- ブランチ内のコミットは目的ごとに分ける
- 実装 → 対象テスト → Lint とセキュリティ検査 → 差分確認 → PR 作成の順に進める
- 検証がすべて成功した場合にのみ、merge commit 方式で `main` へマージする
- squash merge と rebase merge は使用しない。分割したコミットを履歴に残す
- マージ後は作業ブランチをリモートとローカルの両方から削除する
- 検証失敗、競合、未コミット変更がある状態ではマージしない
- 先行するタスクの完了条件を満たさないまま、次のタスクへ進まない
- 各 Phase は網羅性ではなく、前後の機能と接続された最小の垂直スライスとして完成させる
- 将来 Phase の機能を先行実装しない
- Phase をまたぐ変更が必要になった場合は、実装前に本書と実行キューを更新する

## P13 の開始条件

P13 は、次のいずれかが実際に発生するまで着手しない。

- 組織からホスティング提供の具体的な要望が届く
- 継続的な利用希望が複数確認される
- セルフホスト導入支援だけでは解決できない需要が確認される
- 運用費用を賄える契約の可能性がある

認知獲得だけを目的として、常設の公開環境を先行して用意しない。

# OfficeWeave 全体ロードマップ

本書は中長期の Phase、目的、開始条件、完了条件だけを記録する。
Phase の順序と内容を変更する場合は、本書を更新したうえで行う。

現在地と実行順は本書には書かない。正本は [実行キュー](execution_queue.md) だけとする。

## 進行情報の責任分界

進行に関わる情報は、次の 4 か所で役割を分ける。同じ情報を複数箇所へ複製しない。

```text
docs/roadmap.md
  中長期の Phase、目的、開始条件、完了条件
docs/execution_queue.md
  現在地、次のタスク、実行順、タスク状態
GitHub Issue
  不具合の再現、影響、修正方針、完了条件
GitHub PR と Git 履歴
  実際の変更、検証結果、マージ証跡
```

### CI の導入時期

CI は P2 では扱わず、P12 完了後の最終工程 F でのみ導入する。

P2 の目的は、開発者が手元で品質を確認できる状態を作ることである。
検証手段が固まる前に CI を組むと、実装途中の暫定的な手順が設定として固定され、
毎 Phase で CI 設定の保守が発生する。

したがって P2 から F までは、すべての検証をローカルで実行する。
F では、その時点で確立した検証コマンドをそのまま CI へ移す。

### 開発制御ツールについて

外部の開発制御ツールは導入しない。

進行状態はロードマップと実行キュー、および Git の履歴で管理する。
1 タスク 1 ブランチ 1 PR を守れば、`git log` と PR 一覧から現在地を復元できるため、
専用ツールを実行環境へ持ち込む必要がない。

以前のロードマップにあった Agent 向け read/write scope の固定タスクも取りやめる。
変更範囲は、実行キューの各タスク定義とブランチ単位の差分で表現する。

## R0 以降の位置づけ

P0 から F までで、セルフホスト版の機能範囲と検証手段は一巡した。
ただし F 完了後の静的レビューで、データ消失と外部への到達に関わる不具合が確認された。
機能を足す前に、これらを解消する Phase を R0 として置く。

R1 以降は、現時点で不具合ではないが、実運用へ入る前に必要と判断した項目である。
不具合は GitHub Issue で管理し、機能追加は本書で管理する。両者を混ぜない。

### R0 安定化

登録済みの不具合 Issue を、重大度と依存関係の順に修正する。
新しい機能を足さない。修正の範囲は Issue の完了条件に閉じる。

Issue の実行順は [実行キュー](execution_queue.md) に記録する。

R0 の最後には、全 Issue、全検証、文書、配布構成の整合を確かめる安定化完了監査を置く。
R0 が完了するまで、GitHub Release による公開リリースは作成しない。

R0-T21 までの範囲は完了した。監査の結果は [実行キュー](execution_queue.md) に記録する。

その後のセキュリティレビューで、認証、出力、監査、権限に関わる不具合を
新たに 4 件登録した。いずれも R0 の対象と同じ性質であるため、新しい Phase を
足さず、R0-T22 から R0-T25 として同じ方針で処理した。R0-T26 で結果を
確認し、R0 は完了した。

Content-Security-Policy の不在は、このレビューでも確認している。R5 に
計上済みの項目であるため Issue へは登録せず、本書で管理する。

開発制御の専用ツールは、P0 で決めたとおり今後も導入しない。
進行状態は実行キューと Git の履歴だけで管理する。

### R1 運用信頼性

- バックアップの定期実行、保持期限、暗号化
- 監査記録の保持期間と出力
- 構造化ログ
- 稼働監視と運用通知

いずれも機能の追加であり、不具合ではない。GitHub Issue では管理せず、
本書と [実行キュー](execution_queue.md) だけで扱う。

記録や書庫を消す機能は、設定した組織だけが受け取るものとする。
設定しないまま入れ替えた組織で、これまで残っていたものが消えてはならない。
保持の上限は既定を持たず、明示した場合にだけ働く。これを R1 の完了条件へ含める。

### R2 認証・アカウント

- 自分のパスワード変更
- パスワード再設定
- 実際の OIDC 連携
- セッションの一覧と一括終了
- API トークンの権限と有効期限

いずれも機能の追加であり、不具合ではない。GitHub Issue では管理せず、
本書と [実行キュー](execution_queue.md) だけで扱う。

セッションの期限の設定化は、運用先から変更要求が確認された場合にだけ扱う。
現時点で要求は確認されていない。R2 の着手条件ではない。

資格情報を扱う機能は、外部の認証方式へ切り替えた環境では働かせない。
パスワードがこの製品の中に無い環境で、変更や再設定の経路を出すと、
利用者はそこで変えたつもりになる。これを R2 の完了条件へ含める。

発行済みの資格情報の扱いを、この Phase で狭めない。API トークンへ権限と
期限を足す際も、既に発行された token の使える範囲を後から狭めない。

### R3 業務機能

- 多段承認
- 代理承認
- 承認経路のスナップショット
- 予約の変更
- 繰り返し予定
- 予定の参加者
- 部門の CSV 取込

部門の CSV 取込は、利用者 CSV と同じ復元経路を通してから実装する。
書き出しは数式として解釈されないよう保護しているため、取り込みを素通しで
足すと、保護用の文字がそのまま部門名として保存される。
これは R3 のブロッキング前提とする。

いずれも機能の追加であり、不具合ではない。GitHub Issue では管理せず、
本書と [実行キュー](execution_queue.md) だけで扱う。

既にある記録の意味を変えない。多段承認と代理承認を足す際も、
進行中の申請の承認者と状態を、後から別の意味へ読み替えない。
これを R3 の完了条件へ含める。

- 一覧のページネーション
- 一覧の絞り込み
- API のページングとレート制限
- 検索対象の拡張

### R5 品質・セキュリティ

- 実ブラウザーによる E2E
- 自動アクセシビリティ検査
- Content Security Policy
- コンテナの脆弱性検査
- SBOM の生成
- GitHub Actions 参照の SHA 固定
- 性能・負荷検証

各項目の実装方式とライブラリは、着手時に決める。本書では固定しない。

### R6 保守性

R0 の完了後に行った保守性のレビューで、次の 3 種類の問題を登録した。

- 同じ記述が複数の場所へ写され、片方だけが変わり得る状態
- 実装と食い違ったまま残り、従うと現状と違うものを作る文書
- 管理にかかる手間が、そこから得られるものに見合わなくなった記録

いずれも利用者に見える振る舞いを変えない。
振る舞いを変える必要が生じた場合は、R6 では扱わず別に登録する。

不具合と同じく GitHub Issue で管理し、実行順は [実行キュー](execution_queue.md) に記録する。

### R7 脆弱性対応

セキュリティレビューで確認したものを、[脆弱性の報告](../SECURITY.md) の方針に従って
非公開の Draft Security Advisory として登録し、1 件ずつ修正する。

不具合と違い、公開の Issue では管理しない。登録先と経緯は Advisory が持つ。
本書と [実行キュー](execution_queue.md) には、タスクと実行順だけを記録する。

修正の範囲は、Advisory に書いた完了条件とスコープ外に閉じる。
同じ経路で見つけた別の弱点は、その Advisory へ足さず新しい Advisory として登録する。

### R8 性能

R7 の完了後に行った性能のレビューで、次の 3 種類の問題を登録した。

- 処理の対象の数だけ問い合わせが増える経路
- 画面へ出さない列と行まで読み込む経路
- 絞り込みの条件に合う索引が無く、蓄積した記録を毎回走査する経路

いずれも、入力が小さいうちは現れない。大きくなったときに比例して重くなる。
1 件ずつ、実測を根拠に取り除く。

R4 の規模・操作性とは分ける。R4 はページネーションや絞り込みという機能の追加
であり、R8 は機能を変えずに同じ結果をより少ない読み込みで得ることである。
R5 の性能・負荷検証とも分ける。R5 は測る手段の追加であり、確認済みの問題の
修正ではない。

不具合と同じく GitHub Issue で管理し、実行順は [実行キュー](execution_queue.md) に記録する。

### R9 開発体験

R8 の完了後に行った開発体験のレビューで、次の 3 種類の問題を登録した。

- 機能を提供しないまま、依存・検証・配信に残っている基盤
- 同じ契約が複数の模型へ写され、片方だけが変わり得る状態
- 実際の開発経路と食い違ったまま残っている標準コマンド

R6 の保守性とは分ける。R6 は「利用者に見える振る舞いを変えない」ことを前提に、
記述の重複と文書の食い違いを扱った。R9 は配信する HTML と開発コマンドの契約が
変わるものを含む。前提が違うため、同じ Phase では扱わない。

削る量では判断しない。現在かかっている保守の手間、変更時の二重作業、
更新を落としたときの危険、コマンドの実際の挙動を根拠にする。

不具合と同じく GitHub Issue で管理し、実行順は [実行キュー](execution_queue.md) に記録する。

## 進行規則

- 1 タスクにつき 1 ブランチ 1 PR とし、独立して検証できる単位まで分解する
- ブランチ名は `p<Phase>/t<連番>-<短い英語>` とする
- ブランチ内のコミットは目的ごとに分ける
- 実装 → 対象テスト → Lint とセキュリティ検査 → 差分確認 → PR 作成の順に進める
- 検証がすべて成功した場合にのみ、merge commit 方式で `main` へマージする
- squash merge と rebase merge は使用しない。分割したコミットを履歴に残す
- マージ後は作業ブランチをリモートとローカルの両方から削除する
- 検証失敗、競合、未コミット変更がある状態ではマージしない
- 先行するタスクの完了条件を満たさないまま、次のタスクへ進まない
- 各 Phase は網羅性ではなく、前後の機能と接続された最小の垂直スライスとして完成させる
- 将来 Phase の機能を先行実装しない
- Phase をまたぐ変更が必要になった場合は、実装前に本書と実行キューを更新する

## P13 の開始条件

P13 は、次のいずれかが実際に発生するまで着手しない。

- 組織からホスティング提供の具体的な要望が届く
- 継続的な利用希望が複数確認される
- セルフホスト導入支援だけでは解決できない需要が確認される
- 運用費用を賄える契約の可能性がある

認知獲得だけを目的として、常設の公開環境を先行して用意しない。

# 0001 製品範囲を 3 つの段階に分ける

- 日付: 2026-08-05
- 状態: 採用

## 状況

README は「セルフホスト版として想定した機能範囲と検証手段は、ひととおり実装しています」
と書いていた。この記述は、[製品ビジョン](../vision.md) の範囲だけを基準にすれば正しい。

一方、リポジトリを読むと、次のような未達が残っている。

- 更新の経路の多くが監査へ残らない。運用管理の記述と一致しない
- 決裁の権限を、申請の行を確保する前の段に対して判定している
- 多段の経路で中間の段を承認すると、段の進行を確定したあとに応答が失敗し得る
- 通知の重複判定が対象ごとで、正当な再通知まで作られない
- 主要な一覧の一部に上限が無い
- 保存物の改ざんを、復元の前に検出しない

「実装した」と「実運用に耐える」を同じ語で表しているため、
README は誤りではないのに、読む側へ誤った期待を与える。

さらに、掲示、メッセージ、在席、報告のように、いま経路を持たない業務機能について、
範囲へ入るのか入らないのかが、どの文書にも書かれていない。
進行管理の帳簿は畳んだため（`06576c5`）、その判断を置く場所も無い。

## 判断

機能を 3 つの段階へ分ける。

```text
Core      すでに入口を持つ機能。実運用に耐える深さまで仕上げる
Suite     正式な範囲だが、まだ入口を持たない機能
Extended  範囲へ含めるかどうかを、まだ決めていない領域
```

入口は画面の経路に限らない。運用のコマンドと定期実行も数える。
経路だけを見ると、バックアップや診断のように画面を持たない機能が
どの段階にも入らない。

段階とは別に、種類を 3 つ持たせる。

```text
capability          利用者、管理者、運用者が使う機能
cross_cutting_gate  特定の機能に属さない横断の品質
release_gate        版全体の検証
```

加えて、「実装済み」と「本番準備済み」を別の語として定義する。
前者は受入条件を満たしたこと、後者は対象の commit に対する検証の記録があることとする。

正本は `docs/product/` に置く。決め方は [製品範囲](../product/product_scope.md)、
判定の条件は [受入条件](../product/acceptance_criteria.md)、
機能ごとの結果は [機能到達度](../product/capability_matrix.md) が持つ。

## 理由

### 足す作業と仕上げる作業を分けるため

同じ列に並べると、足す側が常に選ばれる。足す方は結果が見え、
仕上げる方は見えないためである。段階は、この 2 つを混ぜないために置く。

### 「実装済み」の意味を 1 つにするため

意味が揃っていないと、機能ごとに読む側が解釈することになる。
条件を 1 か所に書き、機能ごとの判定をそこへ従わせる。

### 決めていないことを、決めていないと書けるようにするため

メールや任意の業務アプリは、単独の製品に相当する量を持つ。
`planned` と書けば作る約束になり、書かなければ検討していないことになる。
`deferred` を持たせて、決めていない状態のまま置けるようにする。

## Suite として 19 件を採用する

Suite へ入れてよいのは、製品ビジョンまたは決定記録で正式に採用したものだけと
定めた。その採用をここで行う。到達度への登録だけを採用の代わりにすると、
一覧へ書き足すだけで正式な範囲が広がり、閉じた集合にした意図が失われる。

次の 19 件を Suite として採用する。識別子は以後変えない。

```text
suite.dashboard_layout          入口の部品配置
suite.global_search             横断検索
suite.calendar_views            予定の暦表示
suite.availability_response     空き時間と出欠
suite.event_series              予定の系列
suite.resource_timeline         設備の時間軸
suite.document_folders          文書の階層と権限
suite.document_versions         文書の版とごみ箱
suite.board_posts               掲示
suite.application_roles         機能別の運用権限
suite.internal_messages         内部メッセージ
suite.personal_notes            個人メモ
suite.todos                     ToDo
suite.presence_and_phone_memos  在席と電話メモ
suite.address_book              アドレス帳
suite.shared_links              リンク集
suite.reports                   報告
suite.projects                  プロジェクト
suite.request_forms             申請の様式と経路の種別
```

これ以上を Suite へ足す場合は、新しい決定記録を作る。

採用は着手の約束ではない。Core に未達が残るあいだは、どれにも着手しない。

## 製品ビジョンの非目標から 2 件を外す

メールの送受信と、利用者が定義を作る業務アプリ基盤は、非目標に挙がっていた。
一方で、この 2 つは「保守負担が大きいので、需要を確かめてから決める」領域であり、
「範囲へ含めないと決めた」領域ではない。

非目標に置いたままだと、判定の順序で範囲外へ送られ、採否を決める前に
結論が固定される。決めていないことを、決めたことにしてしまう。

そこで 2 件を非目標から外し、Extended へ移した。
不採用と判断した場合は、そのとき非目標へ戻し、範囲外へ送る。

なお、この変更で範囲を広げたわけではない。実装の着手条件は変わらず、
調査と決定記録が先に必要である。

## 影響

- Core に未達が残るあいだは、Suite の実装へ着手しない
- Core の完了に必要なものは Core へ置く。Suite へ置くと、着手できない条件になる
- README の状態表現を、実装と本番準備で分ける
- 入口を足す変更は、属する機能を機能到達度で決める
- 段階を動かす変更は、その理由を新しい決定記録として残す

## 採らなかった案

### 製品ビジョンだけを正本にする

製品ビジョンは、何を解決するかを書く文書である。
到達度を持たせると、目的の記述と進捗の記述が混ざり、どちらも読みにくくなる。

### 段階を持たず、GitHub Issue だけで管理する

Issue は個々の作業を持つ。「いま何ができるのか」は、
開いている Issue を全部読まないと分からない。読む側の費用が大きすぎる。

### 到達度を文書ではなく検査だけで持つ

何を満たせば `complete` かは人が決める必要があり、その定義は文書でしか持てない。
ただし、文書だけでは実装から離れる。次の作業として、
機能と入口・テスト・文書の対応を検査で確かめられるようにする。

## 次に作る一覧が持つ項目

本書で決めた契約を機械が読めるようにするため、次の作業で作る一覧は次を持つ。
Markdown を解析する形にはしない。解析器が正本になると、
書き方を変えるたびに判定が変わる。

```text
id                  安定した識別子。意味を変えて再利用しない
kind                capability / cross_cutting_gate / release_gate
stage               capability だけ。範囲外は持たない
state               capability と cross_cutting_gate
result              release_gate だけ
implementation_paths
routes_or_entries
tests
documents
criteria            条件ごとに 満たす / 未達 / 非該当 / 未評価 と、理由と証拠
replacement         外部連携で代替した機能の置き換え先
```

検査は次を失敗として扱う。

```text
complete に 未達 または 未評価 の条件がある
非該当 に理由が無い
記載した path が存在しない
段階と状態の組合せが許可表に無い
rejected に段階が付いている
release_gate に capability の状態が付いている
置き換え先の識別子が存在しない
識別子の意味を変えた、または再利用した
```

## 畳んだ帳簿との違い

削除したロードマップと実行キューは、完了した作業の記録だった。
PR と `git log` の写しであり、更新の手間だけが増えていた。

本書と機能到達度が持つのは、現在の到達度である。
写しにならないよう、作業の順序と進行は持たせない。それらは Issue と PR が持つ。

# OfficeWeave 継続的インテグレーションの構成

本書は maintainer 向けである。寄稿者が読む必要は無い。手元で `bin/verify` が
通れば自動実行も通る、という点だけが寄稿者に関わる（[品質基盤](../development/quality.md)）。

## 分け方

手順の一覧は作り直さず、`bin/verify` をそのまま呼び出している。
検証内容が 2 か所で管理されると、手元と自動実行で結果が食い違う。

走らせる場面で 2 つに分ける。判断は「この変更で壊れ得るか」で行う。
壊れ得ないものを毎回走らせると、待ち時間だけが増える。増えた分は、やがて
結果を見ずにマージする習慣として返ってくる。

### 変更を出すたびに走るもの（`.github/workflows/verify.yml`）

何をどの実行環境で走らせるかは workflow が持つ。本書へ写さない。
写すと、仕事を分けるたびに 2 か所を直すことになる。

すべてを同時に走らせる。1 つが落ちても残りは最後まで走らせ、落ちた範囲だけ
を見て直せるようにする。

書式とセキュリティだけコンテナを使わないのは、この範囲がデータベースへ
触れないためである。触れない以上、クライアントの系列を揃える条件も掛からず、
実行環境を組み立てる理由が無い。理由は
[テストの組み立てをやめない理由](#テストの組み立てをやめない理由) に書く。

workflow へ渡すのは範囲の名前だけとし、どのコマンドを流すかは `bin/verify`
が決める。手順を写すと一覧が 2 か所になり、`config/verify.rb` へ検査を
足しても自動実行がそれを流さない状態が、黙って生まれる。

範囲や分割の挙げ忘れは `test/configuration/verification_scope_test.rb` と
`test/lib/tasks/test_files_test.rb` が見る。実行されない範囲があっても、
残りの範囲は緑になるため、結果からは気付けない。

同じ枝へ続けて出した場合は、古い実行を止める。止めないと、寄稿者は自分が
捨てた commit の結果を待つことになる。実行の順番も保証されないため、古い方
が後に終わって最後の結果として残り得る。`main` では止めない。そこへ入った
ものは、どの commit も結果を残す必要がある。

### main へ入ったあとに走るもの（`.github/workflows/operations.yml`）

こちらも一覧は workflow が持つ。いずれも配布用の構成とホスト側の手順を
見るものであり、コンテナ内のテストとしては実行できない。

こちらは週次でも走らせ、手動でも実行できる。脆弱性の検査は、こちらが何も
変えなくても結果が変わる。変更が止まっている間に検査まで止めない。

後者を分けているのは、いずれも起動と後片付けを含み、変更のたびに動くもの
ではないからである。これらへ触れる変更を出す場合は、手元で通してから
PR を出す。

`bin/verify` 以外を独立した仕事にしているのは、いずれも Docker やホスト側の
操作、または追加の service を必要とし、コンテナ内のテストとして実行できない
ためである。

配布用の構成の確認を分けているのは、開発用で通ることと、
配布したものが動くことが別だからである。
実際、この確認によって、鍵がイメージへ焼き込まれていた問題が見つかった。

両方が必ず走ることは `test/configuration/verification_scope_test.rb` が
確かめる。片方が走らなくなっても、その場では何も失敗しない。緑のまま、
確かめていない状態が続く。

## 組み立てた層を持ち越す

依存の解決は、依存の定義が変わらなければ毎回同じ結果になる。実行のたびに
やり直すと、その待ち時間が変更を出した人へそのまま乗る。

組み立ては Docker 公式の動作へ任せ、層を実行の間で持ち越す。書き出す側は
`verify.yml` だけとする。両方から書くと、同じ鍵へ同時に書き込み、
先に終わった側の内容が捨てられる。

イメージの名前は compose が使うものへそろえる。食い違うと、持ち越した層が
使われず、compose が改めて組み立て直す。

## 待ち時間

**実測の値を本書へ書かない。** 実行ごとのばらつきが大きく、ソースの取得に
1 秒かかる回と 1 分以上かかる回がある。1 回の値を書くと、次に読む人はそれを
現在の値として読む。いま何秒かは、GitHub Actions の実行の一覧が持つ。

短くしてある手立ては次のとおりである。

```text
範囲を分けて同時に走らせる      落ちた範囲だけを見て直せる
組み立てた層を実行の間で持ち越す  依存の定義が変わらなければ組み立て直さない
```

## これ以上は詰めない

残る手立ては次のとおりで、いずれも取らない。

| 手立て               | 引き換えに失うもの |
| ------------------ | --------- |
| テストの実行環境の組み立てをやめる | コンテナで確かめること |
| テストを減らす           | 退行に気付ける範囲 |

### テストの組み立てをやめない理由

`config.active_record.schema_format = :sql` のため、スキーマ定義の読み書きが
`psql` と `pg_dump` を通る。この製品は、取り込むクライアントの系列を
データベースの系列と一致させることを条件にしており、
`test/configuration/runtime_version_test.rb` がそれを検査している。
理由は「版が違うと、スキーマ定義の書き出しとバックアップの取得が失敗する」
ことである。

実行環境に入っているクライアントはこれより古い。合わせるには実行のたびに
導入することになり、導入の時間が縮めた分をそのまま食う。合わせずに使えば、
自分で「揃っていること」と定めた条件を、自動実行だけ外すことになる。

書式とセキュリティで組み立てをやめられたのは、この条件が掛からないためで
ある。接続を必要としない検査に、条件は及ばない。

### 残りはこちらで動かせない

実測が長引いた回は、いずれもソースの取得か脆弱性の一覧の更新で待たされて
いる。どちらも GitHub と github.com の間の待ちであり、こちらでは動かせない。

## 増やすときの予算

短くしたものは、放っておくと元へ戻る。検証は増える方向にしか力が働かない。
1 つ足すときの理由はいつも正当であり、増えた合計を見る機会が無い。気付くのは、
結果を待たずにマージする習慣がついたあとである。そうなると、増やした検査
そのものが働かなくなる。

上限を置く。増やすことは禁じない。黙って増えることだけを防ぐ。

区分と上限の正本は `test/configuration/verification_budget_test.rb` とする。
本書へ写さない。写すと、上限を動かすたびに 2 か所を直すことになる。

数えるのは、変更を出すたびに走る仕事の数、そのうち実行環境を組み立てる
仕事の数、そして変更を出すたびに走る検査の数である。超えると落ち、区分
ごとの案内が出る。

引き上げる場合は、上限を動かす差分に理由を添える。**上限へ触れる
ことそのものが目的である。**置き場所を 1 度考える機会を作る。

### 予算に入れないもの

| 対象         | 理由                              |
| ---------- | ------------------------------- |
| テストの件数     | 増えてよい。増えた分は分割で吸収する。縛ると退行に気付けなくなる |
| 所要時間       | 実行環境の速さが結果に入り、変更と無関係な失敗が出る      |
| 運用の検証の仕事の数 | main へ入ったあとに走る。誰も待たない           |

数えるのは構造だけとする。時間で縛ると、上限に触れて落ちるようになり、
やがて上限そのものが信用されなくなる。

速くする必要が再び出た場合は、まずテストの実行環境の用意を見る。
テストの分割ではない。

## 外部の動作の参照

workflow が参照する外部の動作は、commit の識別子で固定する。

```yaml
uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
```

移動する tag（`v4` など）で参照すると、参照先の中身が後から変わる。
検証を実行する環境は、リポジトリの内容と CI の秘密情報へ触れる。

版は注記として残す。識別子だけでは、どの版を指しているのかが読めない。

固定されていることは `test/configuration/workflow_reference_test.rb` が確かめる。
新しい参照を足したときも、固定を忘れれば失敗する。

更新は手作業とする。自動で追随する仕組みは入れない。固定した意味が薄れる。
版を上げる判断は、依存の更新と同じ扱いにする。

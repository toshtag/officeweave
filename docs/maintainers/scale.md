# OfficeWeave 想定規模での測定

本書は、想定規模のデータの作り方と、測り方を持つ。

**測った値は本書へ書かない。** 実行環境で変わり、変更のたびに古くなる。
版ごとの実測は [版ごとの検証](../releases/) が持つ。

測るのは 1 回の要求が読み込む量である。速さそのものは実行環境で変わるため、
値そのものより、規模を上げても増えないことに意味がある。

## 1. 想定規模

```text
利用者 400 人、主要な記録が各 1 万件
```

この規模を、版の判定に使う想定規模とする（[受入条件](../product/acceptance_criteria.md)
の「4. 実装済みと本番準備済み」）。実装の上限ではなく、判定のときに必ず
その量で測ると決めた量である。

## 2. データの投入

規模は利用者の数で指定する。1 人あたりに積む件数は `LoadSample::PER_USER`
が持つ。本書へ写さない。

```bash
docker compose exec -T -e LOAD_SAMPLE_SCALE=400 web bin/rails officeweave:load_sample
```

何をどれだけ積んだかは、この実行そのものが出力する。積んだ件数を本書へ
写すと、規模の決め方を変えたときに、両方を直すことになる。

専用の組織（`load-sample`）へ積む。既にある組織の記録には触れない。
何度実行しても同じ状態になる。足りない分だけを書き込む。

投入は開発用の構成に対して行う。配布用の構成へ積むと、業務のデータと
混ざったまま消せなくなる。

## 3. 測定

投入した組織の利用者でログインし、主要な画面を開く。

```text
利用者  measure@load-sample.invalid
```

読み込む量は応答の大きさで見る。1 回の要求が返す量が、その画面の上限である。

同時に要求が来る状態は `script/measure_load` で測る。

```bash
BASE_URL=http://127.0.0.1:3210 \
LOAD_MEASUREMENT_EMAIL=measure@load-sample.invalid \
LOAD_MEASUREMENT_PASSWORD=... \
script/measure_load
```

## 4. 何を見るか

いずれの一覧も、記録の数に比例しないことを見る。1 ページ分、または期間の
内側の 1 ページ分だけを読むためである。比例していれば、上限を持たない
一覧が残っている。

上限を入れる前後で、実際にどれだけ違ったかは
[決定記録 0003](../decisions/0003_list_limits.md) にある。

## 5. 問い合わせの数

記録を増やしても問い合わせの数が増えないことは、
`test/controllers/list_query_count_test.rb` が固定する。記録を 1 件だけ足した
状態と、さらに増やした状態で数え、同じであることを確かめる。

絶対の件数は書かない。書くと、無関係な変更のたびに書き換えが要る。

## 6. 選択欄

利用者・部門・設備を選ばせる欄は、並べる候補に上限を置く（`Candidates`）。
上限を超える組織では、絞り込みで残りへ到達する。

上限が無ければ、組織の利用者の数だけ入力欄がそのまま加わる。読み込む量も、
キーボードで送る回数も、その数に比例する。

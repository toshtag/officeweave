# 0.3.2 の検証

本書は、版 0.3.2 を本番準備済みと判定した根拠を持つ。

判定の条件は [受入条件](../product/acceptance_criteria.md) の「4. 実装済みと本番準備済み」にある。
条件ごとの判定は [機能到達度の一覧](../product/capability_registry.yml) が持つ。

## 対象

```text
版        0.3.2
commit    9ed3ac7edcb851717df59d420dfdaf1866c81b6a
判定日     2026-08-07
```

**この commit の `VERSION` は `0.3.2` である。** 版数は実測の前に決めた。

`0.3.2` として公開する木は、この commit に本書と README の更新を重ねたものである。
実測はすべて上記の commit に対して行った。

差が記録だけであることは `script/check_release_source` が確かめる。許す道は
`CHANGELOG.md`、`README.md`、`docs/` だけである。いずれも `.dockerignore` で
配布する image からも外してある。

## この版で直したもの

0.3.1 は、版数を実測のあとに変えてよいものとして扱っていた。

```text
0.3.1 の実測 commit  ad2b1e49（この木の VERSION は 0.3.0）
0.3.1 の公開 commit  763af775（この木の VERSION は 0.3.1）
```

版数は読み物ではない。

```text
config/initializers/version.rb   実行時に読み、OfficeWeave::VERSION になる
bin/rails officeweave:sbom       書き出す部品表の版数に入る
bin/backup                       書庫の metadata の application_version に入る
Dockerfile.production            配布する image へ焼き込まれる
```

したがって 0.3.1 では、測った木と配った木で版数が違う。`README.md` と
`CHANGELOG.md` も `.dockerignore` に無く、配布する image へ入っていた。記録を
書き足しただけで image が変わる状態だった。

0.3.2 では、版数を許す道から外し、読み物を image から外し、版数を実測の前に
決める手順にした。

## 環境

実測は、開発用の構成とは別に作った、破棄できる環境で行った。開発用の
データベースに残るデータは使っていない。負荷測定用のデータは、この環境へ
新しく投入したものである。

```text
構成      compose.production.yaml（配布用）
イメージ   Dockerfile.production から組み立て
設定      .env.example の複製へ、必須の値だけを埋めたもの
ホスト     Darwin 25.5.0 / Docker Compose
データベース postgres:18.4-bookworm
```

環境は、測定を終えた時点で破棄した。

このホストでは、測定のあいだ他の検証も動いていた。時間の値はその状態での
ものであり、0.3.1 の記録より長いものがある。速さは合否に使わない。

結果  passed

### 新規の導入

`.env.example` を複製し、`DATABASE_PASSWORD`、`SECRET_KEY_BASE`、
`APPLICATION_HOST`、`WEB_PORT` を埋めただけの状態から起動した。

```text
docker compose -f compose.production.yaml up -d --build   69 秒（exit 0）
3 つとも healthy                                          402 秒
/health                                                  200（Host: localhost）
script/seed_initial_user --production                    初期利用者を作成
bin/diagnose                                             exit 0
  確認 19 件、注意 1 件、失敗 0 件
```

1 回目の `up` が exit 0 で終わり、2 度目の実行を必要としない。

healthy までの 402 秒は、同じホストで実ブラウザーの検証を終えた直後に測った
ためである。後段で同じ構成を組み直したときは 16 秒から 69 秒で揃っている。

注意の 1 件は `APPLICATION_HOST` が `localhost` であることによる。測定用の
環境の設定であり、実際の配布先では利用者が接続するホスト名を設定する。

### 診断のコマンド

```text
bin/diagnose                                 exit 0（失敗が無い場合）
bin/diagnose                                 exit 1（失敗がある場合）
秘密情報の値                                   出力に 0 件
```

失敗がある状態（管理者が不在）で 1、そうでない状態で 0 を返すことを実際に
確かめた。出力へ `DATABASE_PASSWORD`、`SECRET_KEY_BASE`、初期パスワードの値
そのものが現れないことも確かめた。

負荷測定のあとは注意が 2 件になる。2 件目は、失敗したジョブが 304 件あること
による。宛先が実在しない測定用のデータへ通知を送ったためであり、製品の欠陥
ではない。

# 0.3.1 の検証

本書は、版 0.3.1 を本番準備済みと判定した根拠を持つ。

判定の条件は [受入条件](../product/acceptance_criteria.md) の「4. 実装済みと本番準備済み」にある。
条件ごとの判定は [機能到達度の一覧](../product/capability_registry.yml) が持つ。

## 対象

```text
版        0.3.1
commit    ad2b1e49b591beecfc97a02df6ead2e703f63825
判定日     2026-08-07
```

`0.3.1` として公開する木は、この commit に本書と版数の更新を重ねたものである。
実測はすべて上記の commit に対して行った。

差が記録だけであることは `script/check_release_source` が確かめる。この版の
時点で許す道は `VERSION`、`CHANGELOG.md`、`README.md`、`docs/` だった。

**この版の判定には、あとから見つかった穴がある。** `VERSION` を記録として
許していたため、実測したのは版数 `0.3.0` の木であり、公開したのは版数
`0.3.1` の木である。版数は読み物ではなく、実行時に読まれ、部品表と書庫の
記録に入り、配布する image へ焼き込まれる。したがって「実行時と組み立ての
入力は実測のあと変わらない」は、この版では成り立たない。`README.md` と
`CHANGELOG.md` も配布する image へ入っていた。

穴は [0.3.2](0.3.2_verification.md) で塞いだ。本書の実測そのものは、下に
書いたとおりに行っている。

## この版で直したもの

版の状態を伝える正本が互いに食い違っていた。読んだ場所によって、
「本番準備済み」と「未達が残る」の両方が読めた。

```text
README        冒頭「Core 26 機能は受入条件をすべて満たす」
              末尾「受入条件を満たした機能は 1 件」
受入条件       規範の文書が「docs/releases/ は存在しない」「評価 0 件」を持っていた
機能到達度      「版ごとの評価 0」「判定に使う検証の記録がまだ無い」
公開手順       特定の版番号（0.2.0）を固定していた
```

いずれも実装の欠陥ではない。仕上げた側の文書だけを直し、前に書いた現況を
残したために生まれた食い違いである。

## 0.3.0 に残っていた問題

`script/check_release_source` を入れた結果、0.3.0 の公開そのものに問題が
見つかった。

```text
実測した commit  59be7b279106d62f7070852dceb7b7a1ee24b126
v0.3.0 の commit  df1f851a0f2e362048dada18f590e7b3b0d78bb5
差               test/configuration/completion_registry_test.rb
```

`0.3.0` として公開した木は、そのテストを通していない木である。動作に関わる
差ではないが、実測の対象と公開の対象が一致しているという主張は、0.3.0 では
成り立たない。0.3.1 では成り立つ。

実測は、開発用の構成とは別に作った、破棄できる環境で行った。開発用の
データベースに残るデータは使っていない。負荷測定用のデータは、この環境へ
新しく投入したものである。

```text

ホスト     Darwin 25.5.0 / Docker Compose
データベース postgres:18.4-bookworm
```

環境は、測定を終えた時点で破棄した。

## 実測

### 一括検証

```text
bin/verify                                  exit 0    2 分 37 秒
  書式: Ruby                                481 files inspected, no offenses detected
  セキュリティ: 依存の脆弱性                   No vulnerabilities found
  セキュリティ: 静的解析                      No warnings found
  テスト: 全件（実ブラウザーを除く）             2141 runs, 9738 assertions, 0 failures, 0 errors

```

並行の実行数を 1 にして走らせた。同じホストで他の環境も動かす場合、並行で
走らせるとデータベースが待ち合いを検出して落ちる。これは製品の欠陥ではなく
測定環境の混み具合であるが、記録として残す。

```text
script/check_compose_isolation              exit 0
script/check_release_source                 exit 0
```

### 実ブラウザー

```text
bin/rails test:browser                      exit 0    2 分 8 秒
  45 runs, 221 assertions, 0 failures, 0 errors
```

まとめて実行した結果である。個別の実行では代えていない。

0.3.0 の時点では 24 件だった。画面を持つ Core 21 件それぞれについて、
キーボードだけで主要な操作を完遂する確認を足したためである。

### 外部認証に相当する確認

```text
oidc_login_test, oidc_id_token_test, oidc_claim_contract_test, oidc_client_test
  62 runs, 143 assertions, 0 failures, 0 errors
```

署名の検証、発行者と宛先、期限、nonce、受け取る属性の対応、認可の開始から
戻りまでの流れを、その場で立てた発行者に対して確かめている。実際の認可
サーバーへ接続した確認ではない。

### 新規の導入

`.env.example` を複製し、`DATABASE_PASSWORD`、`SECRET_KEY_BASE`、
`APPLICATION_HOST`、`WEB_PORT` を埋めただけの状態から起動した。

```text
docker compose -f compose.production.yaml up -d --build   45 秒（exit 0）
3 つとも healthy                                          59 秒
/health                                                  200（Host: localhost）
script/seed_initial_user --production                    初期利用者を作成
bin/diagnose                                             exit 0
  確認 19 件、注意 1 件、失敗 0 件
```

1 回目の `up` が exit 0 で終わり、2 度目の実行を必要としない。データベースの
準備は一度きりの `prepare` が持つ。

`127.0.0.1` を宛先にすると 403 を返す。`APPLICATION_HOST` に `localhost` を
設定した環境で、想定外の Host を拒む動作である。

注意の 1 件は `APPLICATION_HOST` が `localhost` であることによる。測定用の
環境の設定であり、実際の配布先では利用者が接続するホスト名を設定する。

### 取得と復元

想定規模のデータを投入した状態で測った。

```text

復元後       お知らせ 10000 件、利用者 402 件
```

書庫の中身を書き換えたものは復元の前に拒む。

```text
改変した書庫  exit 1「書庫の中身が取得したときと違います」
既存のデータ  触れていない（お知らせ 9500 件のまま、利用者 402 件のまま）

```

停止したままにするのは意図した動作である。中途半端なデータで運用を再開させない。

要約が見つけられるのは、壊れと取り違えだけである。書庫ごと作り直されれば
要約も作り直せるため、意図して書き換えた相手は見つけられない。

### 診断のコマンド

```text

bin/diagnose                                 exit 1（失敗がある場合）

```

失敗がある状態（管理者が不在）で 1、そうでない状態で 0 を返すことを実際に
確かめた。出力へ `DATABASE_PASSWORD`、`SECRET_KEY_BASE`、初期パスワードの値
そのものが現れないことも確かめた。

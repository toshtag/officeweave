# OfficeWeave 製品範囲

本書は、機能をどの段階へ置くかの決め方を定義する。

何を解決し、何を解決しないかは [製品ビジョン](../vision.md) にある。
機能ごとにどの段階のどの状態かは [機能到達度](capability_matrix.md) にある。
本書は、その 2 つをつなぐ規則だけを持つ。

## 1. 段階を分ける理由

「実装した」と「実運用に耐える」は別である。両方を 1 つの範囲として扱うと、
先の機能を足す作業と、いまある機能を仕上げる作業が同じ列に並ぶ。並んだ時点で、
足す側が常に選ばれる。足す方が結果が見え、仕上げる方は見えないためである。

段階は、この 2 つを混ぜないために置く。

```text
Core      いまある機能を、実運用に耐える深さまで仕上げる
Suite     正式な範囲だが、まだ経路が無い機能を段階的に足す
Extended  範囲へ含めるかどうかを、まだ決めていない領域
```

## 2. 段階の決め方

段階は、次の順で判定する。上から順に当てはめ、最初に該当したものを採る。

```text
1. 製品ビジョンの非目標に挙がるか        → 範囲外
2. 採否を決めるための調査が済んでいないか  → Extended
3. すでに入口が存在するか                → Core
4. 正式に採用したものとして登録済みか      → Suite
5. 上記のいずれでもない                  → まだ範囲に無い
```

判定の入力は、そのときのリポジトリの現物とする。
「作る予定がある」ことは Core の根拠にしない。

段階は閉じた集合とする。5 に落ちたものは、どの段階にも属さない。
段階を与える前に、採用するかどうかを先に決める。
「思い付いたものはすべて Suite」にすると、一覧が誰の判断も経ずに育つ。

### 2.1 Core

すでに利用者、管理者、運用者のいずれかへ公開している入口を持つ機能である。

入口は画面の経路に限らない。次をいずれも入口として数える。

```text
画面と API の経路   config/routes.rb にあるもの
運用の入口          bin/ と script/ にあるもの
定期実行            worker が周期で動かすもの
```

経路だけを入口とすると、バックアップや診断のように画面を持たない機能が
どの段階にも入らなくなる。それらは実運用でいちばん先に必要になる。

Core の目標は、機能を増やすことではない。
[受入条件](acceptance_criteria.md) を満たし、本番準備済みへ到達させることである。

Core に未達の機能が残るあいだは、Suite の実装へ着手しない。
着手すると、仕上がっていない土台の上へ機能が積まれ、
あとから土台を直す費用が積んだ分だけ増える。

### 2.2 Suite

正式な範囲だが、まだ入口を持たない機能である。

Suite へ入れてよいのは、次の両方を満たすものに限る。

```text
1. 製品ビジョンまたは決定記録で、正式に範囲へ含めると決めてある
2. 機能到達度へ登録してある
```

Suite の機能は、単体で足すのではなく、Core が持つ共通の仕組みへ接続する。
接続先は、権限、監査、通知、検索、保持期間、書き出し、多言語、到達性とする。
接続しない実装は、Suite に入れたことにしない。

### 2.3 Extended

採否そのものを決めていない領域である。

Extended は「あとで作る」ではなく「まだ決めていない」を表す。
着手の前に、需要、保守費用、セキュリティ上の負担、既存の外部実装で代替できるかを
調べ、次のいずれかを [決定記録](../decisions) へ残す。判断の結果で移動先が決まる。

```text
採用          → そのまま Suite へ移す
外部連携で代替  → 連携の境界を表す新しい機能を Suite へ作る
不採用        → 製品ビジョンの非目標へ足し、範囲外へ移す
```

外部連携で代替する場合、元の機能をそのまま移さない。
「メールの送受信を持つ」と「メール連携の境界を持つ」は別の機能であり、
同じ識別子のまま移すと、識別子の指すものが途中で変わる。

元の機能は [機能到達度](capability_matrix.md) の一覧から外し、
決定記録へ次を残して終える。識別子は別の意味へ転用しない。

```text
元の識別子
判断        外部連携で代替
置き換え先   新しく作る Suite の識別子
```

置き換え先が無いまま一覧から外した状態は、次の作業で入れる検査が拒否する。

調べる前に実装へ着手しない。この領域は、いずれも単独の製品に相当する量を持つ。

### 2.4 範囲外

製品ビジョンの非目標に挙がる領域である。

段階は Core・Suite・Extended の 3 つだけであり、範囲外は第 4 の段階ではない。
[機能到達度](capability_matrix.md) では、段階を持たない `rejected` として並べる。

非目標は「永久に実装しない」ではない。
含める場合は、先に製品ビジョンを更新し、そのうえで段階を与える。

## 3. 段階を動かすとき

段階の移動は、次の場合にだけ行う。

```text
段階なし → Suite       製品ビジョンまたは決定記録で正式に採用した
Extended → Suite       自前で実装することを決定記録で採用した
Extended → 一覧から外す  外部連携で代替すると決めた。境界は新しい Suite として作る
Extended → 段階なし     決定記録で不採用と判断し、製品ビジョンの非目標へ足した
Suite    → Core        入口を公開した
段階なし → Extended     製品ビジョンの非目標から外した
```

外部連携で代替する場合は、Extended から Suite へ移さない。
移る先が別の機能であるため、移動ではなく、終了と新規作成として扱う。

逆向きの移動は行わない。
公開した入口を Core から外す場合は、機能の削除として扱い、変更履歴へ残す。

移動させたときは、[機能到達度](capability_matrix.md) を同じ変更で直す。

## 4. 本書が持たないもの

- 機能ごとの段階と状態。[機能到達度](capability_matrix.md) が持つ
- 状態を判定する条件。[受入条件](acceptance_criteria.md) が持つ
- そう分けた理由。[決定記録](../decisions/0001_product_scope.md) が持つ
- 作業の順序と進行。GitHub Issue と PR が持つ

# OfficeWeave 受入条件

本書は、機能がどこまで到達したかを判定する条件を定義する。

判定した結果は [機能到達度](capability_matrix.md) が持つ。
段階の決め方は [製品範囲](product_scope.md) にある。

## 1. 状態

いずれか 1 つの状態を持つ。

| 状態         | 意味                                       |
| ---------- | ---------------------------------------- |
| `planned`  | 正式な範囲だが、入口も実装もまだ無い                       |
| `partial`  | 入口または実装はあるが、受入条件に未達の項目が残る                |
| `complete` | 受入条件をすべて満たし、証拠が揃う                        |
| `deferred` | 範囲へ含めるかどうかを決めていない                        |
| `rejected` | 範囲へ含めないと判断した                             |

## 2. 種類ごとの扱い

段階を持つのは `capability` だけである。
種類によって、取り得る状態と `complete` の条件が違う。

```text
capability
  段階            Core / Suite / Extended / なし
  状態            下の表のとおり
  complete の条件  第 3 節の証拠と、第 5 節・第 6 節の条件

cross_cutting_gate
  段階            持たない
  状態            planned / partial / complete
  complete の条件  対象の範囲、測定できる条件、検査またはテスト、証拠となる文書

release_gate
  段階            持たない
  状態            持たない。版と commit に対する結果を持つ
  結果            not_evaluated / passed / failed
```

段階は Core・Suite・Extended の 3 つだけである。
範囲へ含めないと判断した機能は、第 4 の段階ではなく、
段階を持たない `rejected` の `capability` として扱う。

### 2.1 段階と状態の組合せ

許可する組合せは次に限る。ここに無い組合せは誤りとする。

| 分類                   | 許可する状態                             |
| -------------------- | ---------------------------------- |
| Core                 | `partial` `complete`               |
| Suite                | `planned`                          |
| Extended             | `deferred`                         |
| 段階なし                 | `rejected`                         |
| `cross_cutting_gate` | `planned` `partial` `complete`     |

Core が `planned` を取らないのは、入口があることが Core の条件だからである。
Suite が `planned` だけなのも同じ理由による。入口を公開した時点で Core へ移る
ため、入口を持つ Suite は存在しない。

`release_gate` は `capability` の状態を使わない。結果だけを持つ。

### 2.2 横断の品質の状態

```text
planned   対象と条件は決めたが、それを確かめる検査もテストも無い
partial   確かめる手段はあるが、条件のうち満たしていないものが残る
complete  条件をすべて満たし、確かめる手段と根拠の文書がそろう
```

`cross_cutting_gate` は特定の機能に属さないため、操作の手順を持たない。
第 3 節の証拠をそのまま当てはめない。代わりに、何を対象とし、
何が成り立てば満たしたと言えるかを、gate 自身が持つ。

## 3. 証拠

`complete` と判定するには、次の 3 つがすべて揃う必要がある。

```text
実装の証拠  入口と、その機能を成立させる実装の位置
検証の証拠  その機能の退行を止めるテスト
文書の証拠  その機能を扱う利用者・管理者・運用者のうち、該当する役割が
            操作または運用の手順を読める文書
```

実装の位置は model に限らない。controller、service、job、task、script の
いずれでもよい。状態を保存しない機能は、独立した model を持たずに成立する。
model を要求すると、そういう機能はどれだけ仕上げても `complete` にならない。

独立した model を持たない場合は、持たない理由を
[機能到達度](capability_matrix.md) へ書く。
次の作業で機械が読む一覧では、`implementation_paths` として扱う。

役割を固定で並べない。画面を持たない運用の機能では、運用の手順が文書の証拠に
なる。利用者向けの手順を一律に求めると、そもそも利用者が触らない機能が
`complete` にならない。

「利用者向けの操作文書」の gate が対象とするのは、画面を持つ機能だけである。

証拠は、リポジトリ内の位置で示せるものに限る。
「対応済み」という記述そのものは証拠にしない。

証拠が 1 つでも欠ける場合は `complete` にしない。
実装と検証が揃い、読む文書だけが無い状態は `partial` とする。

## 4. 実装済みと本番準備済み

版全体の検証は、機能ではなくこの節が持つ。

```text
識別子  release.production_readiness
種類    release_gate
対象    版と commit の組
結果    not_evaluated / passed / failed
現在    not_evaluated
```

`release_gate` は `capability` の状態を使わない。結果だけを持つ。
機能の一覧へ混ぜると、どの機能も進んでいないのに一覧だけが伸びる。

この 2 つを同じ語で表さない。単位が違う。

```text
実装済み      機能の状態が complete である
本番準備済み  版として、この gate の結果が passed である
```

Core の機能が目指すのは `complete` までである。
版として本番へ出せるかどうかは、この gate が別に判定する。
機能がすべて `complete` になっても、この gate を通るまで本番準備済みとしない。

検証の記録は `docs/releases/<版>_verification.md` へ置き、次を含める。

- 対象の commit
- 一括検証の実行結果
- 実ブラウザーを含むテストの実行結果
- 静的解析と依存の脆弱性検査の結果
- 新規導入と、旧版からの更新の結果
- バックアップと復元の結果
- 想定規模のデータでの測定結果

実行できなかった項目は、成功として数えず、実行できなかったこととして残す。
未実施が 1 つでもあるあいだは `passed` としない。

現時点で `docs/releases/` は存在しない。結果は `not_evaluated` であり、
本番準備済みと判定した版は無い。

## 5. Core に共通の受入条件

Core のすべての機能が、次を満たしたときに `complete` となる。

```text
1. 更新の経路すべてに権限の判定があり、組織の境界を越えない
2. 更新の経路それぞれが、監査へ記録するかしないかを明示し、実装と一致する
3. 出来事が通知を伴う場合、宛先と発生の組ごとに通知の記録が 1 件だけ作られる
4. 一覧に上限がある。ページ送りか、指定できる期間のいずれかを持つ
5. 利用者・部門・設備を選ばせる欄が、対象の件数に比例して描画量を増やさない
6. データベースだけで保てる不変条件を、データベース側にも持つ
7. 増え続ける記録に、削除または保管の方針がある
8. その機能が持つ入口、実装、権限の判定、並行した操作に、退行を止めるテストがある
9. その機能を扱う役割が、操作または運用の手順を文書で読める
10. 画面に出る語句が、対応する 2 つの言語に揃う
11. 主要な操作がキーボードだけで完了する
```

上記は、機能を足すたびに確かめる一覧としても使う。

該当しない条件は、満たしたものとして扱う。
状態を変える経路を持たない機能に、条件 2 は問えない。
該当しないと判断した場合は、その理由を [機能到達度](capability_matrix.md) へ書く。
書かずに省くと、確かめ忘れと区別が付かない。

条件ごとの判定は、次の 4 つのいずれかとする。

```text
満たす    条件を満たしている
未達      満たしていない
非該当    その機能には問えない。理由を書く
未評価    まだ確かめていない
```

`complete` は、すべての条件が「満たす」または「非該当」であることを要する。
「未評価」が 1 つでも残るあいだは `complete` にしない。

`partial` では、すべての条件を評価しなくてよい。
到達度に並ぶ未達は、そのとき判明したものであり、網羅を意味しない。

## 6. 機能に固有の受入条件

共通の条件に加えて、次を満たす。ここに挙がらない機能は、共通の条件だけで判定する。

### ログインと資格情報

- 同じ識別の単位に対する試行の上限が、動かしている web の数に依存しない

### 申請と承認

- 同じ利用者が同時に二重で決裁しても、段は 1 つだけ進む
- その段の担当でない利用者は、行を確保したあとの再判定で拒否される
- 承認と差し戻しが競合した場合、片方だけが成立する
- 履歴に残る段の位置、代理元、時刻が、実際に成立した処理と一致する

### 通知

条件は層ごとに分ける。層を分けずに「1 度だけ届く」と書くと、実装できない
条件になる。外部への送信は at-least-once であり、同じメールが二度届くことが
ある（[変更履歴](../../CHANGELOG.md) の補足、[設定](../operations/configuration.md) の
「実行の保証」）。届いた回数を製品の側から抑えることはできない。

```text
業務通知    同じ出来事・同じ宛先について、通知の記録を 1 件だけ作る
配信キュー  同じ通知・同じ配信手段について、配信の記録を 1 件だけ積む
外部配送    at-least-once とし、受け取る側が配信の識別子で重複を判別できる
```

- 差し戻しのあと再提出すると、新しい未読が作られる
- 同じ利用者が複数の段を担当する場合、それぞれの段で作られる
- 同じ処理を再試行しても、通知の記録と配信の記録は増えない
- メール配信を有効にし、配信の条件を満たす通知について、
  画面へ出す通知の記録と、メール配信の記録が対応する

最後の条件は、配信を無効にした利用者、宛先を持たない利用者、
送信を設定していない環境を対象にしない。それらは対応しないことが正しい。

### 承認の委任

- 期間が重なる委任を、並行して作成しても片方だけが成立する

### 設備・備品の予約

- 重なる時間帯の予約を、並行して作成しても片方だけが成立する

### 監査記録

- 更新の経路すべてに、記録する／記録しないの判断が割り当てられている
- 本文、添付の内容、秘密、token を記録しない
- 処理が失敗した場合、記録だけが残らない

### 外部接続 API

- token は、発行時点で明示された範囲の外を拒否する
- 範囲を後から足しても、既存の token へ自動では付かない
- 上限が、動かしている web の数に依らない
- 応答の形が版として固定され、記載の無い項目の削除を検査が拒否する

### 出来事の送信

- 一覧に挙げた出来事が、実際に送られる
- 出来事ごとに形が決まっており、形の版が本文に入る
- 再送、重複、署名の扱いが文書にある

### バックアップと復元

- 1 バイトでも改変された保存物を、復元の前に拒否する
- 想定規模のデータで、取得と復元に掛かる時間と、停止する時間を実測してある

### 導入とアップグレード

- 新規の導入と、旧版からの更新が、同じ commit に対して成功する
- 戻す手順が、実際に戻せることを確かめてある

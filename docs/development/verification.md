# OfficeWeave 総合検証

本書は、公開する前に一度通す確認の手順を定義する。

## 1. 本書の範囲

本書に置くのは、自動では確かめられない確認だけとする。

判断は「テストの実行環境ではなく、実際に起動した構成でしか現れないか」で行う。
現れないものは、ここではなく自動の検証で押さえる。

### 自動で確かめているもの

次は本書では再掲しない。

```text
bin/verify
  書式、依存の脆弱性、静的解析、テスト全件（システムテストを含む）、初期データの投入

.github/workflows/verify.yml
  Compose 構成の分離
  bin/verify（開発用の構成）
  配布用の構成での起動、稼働確認、想定外の Host の拒否、診断
  初期利用者の作成と、資格情報が常駐サービスへ残らないこと
  配布用の構成でのバックアップと復元
  配布用の構成での永続キューと worker
```

何がどのテストで押さえられているかは、テストの名前とコメントが持つ。
本書へ写さない。写すと、同じ内容を 2 か所で保つことになる。

自動実行では、同じホストで複数の検証が並行しうる。
衝突を避けるため、実行ごとに一意な project 名を `-p` で指定している。

### 節を追加してよい条件

不具合を直したことの記録は、CHANGELOG と Issue が持つ。本書へは足さない。

足すのは、`bin/verify` でも CI でも確かめられない確認だけとする。
確かめられるものを足すと、本書は手で通せない分量になり、通されなくなる。

## 2. 手元での一括検証

```bash
docker compose exec web bin/verify
```

コンテナ内では Docker を扱えないため、構成そのものの検査は分けてある。
ホスト側で実行する。

```bash
script/check_compose_isolation
```

開発用と配布用の project 名、データボリューム、公開ポートが分かれていることを確かめる。

## 3. クリーンな環境からの起動

蓄積した状態ではなく、何も無い状態から起動できることを確かめる。
本節は開発用の構成に対して実行する。`-f compose.production.yaml` は付けない。

```bash
docker compose down -v
```

```bash
docker compose up -d --build
```

```bash
curl -s http://127.0.0.1:3210/health
```

```bash
script/seed_initial_user
```

`.env` へ `INITIAL_USER_EMAIL` と `INITIAL_USER_PASSWORD` を設定していない場合、
利用者は作成されず、必要な設定を知らせて終わる。既定の資格情報は用意しない。

```bash
docker compose exec web bin/diagnose
```

## 4. 配布用の構成を、雛形の複製から起動する

導入手順の出発点は `.env.example` の複製である。
そこから必須の値を埋めただけで起動することを確かめる。

```text
1. .env.example を .env として複製する
2. DATABASE_PASSWORD、SECRET_KEY_BASE、APPLICATION_HOST を埋める
3. 配布用の構成を起動する
4. 構成の解決で止まらないことを確かめる
```

雛形に無い必須の変数があると、この手順は 3 で止まる。
どの変数が足りないかは、構成ファイルが名前を挙げて知らせる。

```bash
docker compose -f compose.production.yaml up -d --build
```

CI は既定値を持つ env ファイルを組み立ててから起動する。
雛形そのものからの起動は、ここでしか通らない。

## 5. 開発用と配布用を同じホストで動かす

CI は 2 つの構成を別のジョブで動かす。同じホストへ並べたときの分離は、
ここでしか確かめられない。

公開ポートだけは共有できない。どちらかの `WEB_PORT` を変更する。

```bash
WEB_PORT=3211 docker compose -f compose.production.yaml up -d
```

データの分離は、実際に消して確かめる。

```text
1. 開発用と配布用のそれぞれへ、区別できる記録を入れる
2. 開発用で down -v を実行する
3. 配布用の記録が残っていることを確かめる
4. 逆向きでも同じことを確かめる
```

## 6. 配布するイメージの中身

鍵と接続情報が含まれていないことを確かめる。

```bash
docker run --rm --entrypoint sh <イメージ名> -c 'ls config/master.key .env'
```

いずれも存在しないことが正しい。

## 7. 外部のサービスへ実際につなぐ

テストも CI も、実在する外部の宛先へは接続しない。
到達性と、受け取る側での見え方は、ここでしか確かめられない。

```text
1. 実在する SMTP サーバーを設定し、通知メールが届く
2. 本文の URL が APPLICATION_HOST と APPLICATION_PROTOCOL のとおりになる
3. APPLICATION_PORT を設定した場合、URL にそのポートが入る
4. 実在する Webhook の宛先を登録し、送信が届く
5. 届いた要求に X-OfficeWeave-Delivery-Id がある
```

クラウドのメタデータサービスなど、内部の宛先へは送らない。

書き出した CSV を表計算ソフトで開いたときの見え方も、ここで確かめる。
製品、版、取り込み設定によって異なるため、自動の検証は保護の構造と
往復までしか押さえていない。

```text
6. = + - @ で始まる値が、開いた先で数式として評価されない
```

## 8. 主要な業務の流れ

`test/system/end_to_end_test.rb` が、部門の作成から文書の検索までを
画面の操作だけで通している。手作業での確認は不要とする。

実際に起動した構成でひととおり触れる場合も、確認としてではなく、
画面の見え方を人の目で見る目的で行う。

# OfficeWeave 品質基盤

本書は、コードの検査手段と実行方法を定義する。

検査はどれも手元で実行できる。自動実行は同じ手順を呼ぶだけとし、
自動実行の側へ手順を書き写さない。写すと、手元と自動実行で結果が食い違う。

## 1. 書式検査

Ruby の書式は Rails 標準の設定を基本とする。

```bash
docker compose exec web bin/rubocop
```

自動修正は次のとおり。差分を確認してからコミットする。

```bash
docker compose exec web bin/rubocop --autocorrect
```

### 独自に追加した規則

設定の正本は `.rubocop.yml` とする。値を本書へ写さない。写すと、値を
1 つ変えるたびに 2 か所を直すことになる。

追加は、判断が分かれて指摘が繰り返される箇所だけにとどめる。
規則を増やすほど、本質的でない差分が増える。追加するときは、その理由を
`.rubocop.yml` へ書く。

### 検査対象から外しているもの

除外の正本は `.rubocop.yml` の `AllCops/Exclude` とする。本書へ写さない。
写すと、増減のたびに 2 か所を直すことになる。

外してよいのは、こちらが書いていないコードだけとする。外部由来のものと、
基盤から取り込んだものである。自分で書いたコードを、指摘されたという理由で
外さない。`.rubocop.yml` へ足すときは、その理由をそこへ書く。

### 導入していないもの

ERB と CSS の書式検査は導入していない。

画面の記述傾向は既に固まっており、「対象がまだ無い」ことを理由にはしない。
導入しない理由は、検査したい対象が今のところ書式ではなく構造であることによる。
入力欄の組み立て方や class 名の付け方が分かれていることは、字下げや空白の
規則では検出できない。

導入する場合は、[依存を足すときに確かめること](architecture.md) に従う。

## 2. 静的セキュリティ検査

アプリケーションのコードを対象に、既知の脆弱性の型を検出する。

```bash
docker compose exec web bin/brakeman --quiet --no-pager --exit-on-warn --exit-on-error
```

指摘が出た場合は、実装を修正して解消する。
検出結果を無視する設定を既定で持たない。無視の設定が増えるほど、検査の意味が薄れる。

誤検出であると判断した場合は、次を残したうえで対処する。

```text
指摘の内容
誤検出と判断した根拠
実際に到達し得ないことの説明
```

## 3. 依存の脆弱性監査

依存として取り込んでいるライブラリに、公開済みの脆弱性がないかを確認する。

```bash
docker compose exec web bin/bundler-audit check --update
```

脆弱性の一覧は実行のたびに更新する。取得済みのものをそのまま使うと、
古い一覧で通ったのか、指摘が無いのかを区別できない。

ブラウザーへ配信するスクリプトは持たないため、その監査は行わない。
配信するようになった時点で、その方式に合う監査を検証へ加える。

### 脆弱性が見つかった場合

1. まず更新で解消する
2. 更新できない事情がある場合に限り、`config/bundler-audit.yml` へ識別子を列挙して除外する
3. 除外する場合は、影響を受けない理由、代わりに取っている対策、再確認する時期を
   `config/bundler-audit.yml` へ書き残す

恒久的な除外を作らない。除外は期限付きの判断として扱う。

### 実行の頻度

- 依存を追加または更新したとき
- 版数の更新を検討するとき
- 最終工程で導入する継続的インテグレーションでは毎回

### 部品表

取り込んでいるものの一覧を、外から読める形で書き出す。

```bash
docker compose exec -T web bin/rails officeweave:sbom > officeweave-sbom.json
```

形式は CycloneDX とする。監査は自分たちで実行できるが、脆弱性の報告を
受けた側は、この製品が何を取り込んでいるかを外から知る手段を持たない。

並べるのは、実行に使う gem とその依存を辿り終えた全体である。
開発と試験だけで使うものは並べない。配布するものの部品表であり、
手元の道具は配布していない。

実行環境の情報や設定の値は含めない。部品表は組織の外へ渡ることがある。

継続的インテグレーションでは毎回書き出し、成果物として残す。
公開する版へ添える手順は [リリース手順](../maintainers/release.md) に定義する。

## 4. 配布するイメージの脆弱性検査

依存の監査は `Gemfile.lock` を見る。イメージへ入っている OS のパッケージは
見ない。配布しているのはイメージであり、そこに含まれるものすべてが対象である。

```bash
script/scan_container_image
```

ホスト側で実行する。Docker を必要とし、脆弱性のデータベースを取得するため、
一括検証へは含めない。一括検証は実行のたびに同じ結果になることを条件にしている。

修正版のある指摘があれば失敗する。ただし、確認したうえで非該当と判断したものは
`config/container_scan_exceptions.yml` へ記録して通せる。言語処理系が同梱する
ものなど、版を自分たちで選べない指摘がある。逃げ道が無いと、検査そのものを
外す方へ倒れる。

記録には識別子、対象のパッケージ、入っている版、根拠、再確認の期限を書く。
版が上がれば当たらず、期限を過ぎても当たらない。当たらない記録は無いのと
同じに扱い、検査は失敗する。記録して通した指摘は、検査の出力と報告に残る。
通すことと、見せないことは分ける。

### 検査する対象

| 対象               | 合否 | 理由                            |
| ---------------- | -- | ----------------------------- |
| 配布用の Dockerfile から組み立てたイメージ | 決める | 入れるパッケージを選べる                  |
| 配布用の構成が使うデータベースのイメージ | 決めない | 手立ては tag を上げることだけで、上げても解消しない場合がある |

データベースのイメージを含めているのは、配布しているのが構成の全体だからである。
自分たちが書いた側だけを検査しても、動かすものの半分しか見ていない。

合否を分けているのは、解消できない指摘で検証を止め続けると、失敗を無視する
習慣がつくためである。実際、`postgres:18.4-bookworm` は 18 系で最も新しいが、
含まれる `gosu` に修正版のある指摘が残っている。

### 指摘が見つかった場合

修正版のある指摘は、更新して解消する。
土台のイメージの版、`apt` で入れているパッケージの版が対象になる。

修正版が出ていない指摘では失敗させない。自分たちで解消できない状態で検証が
止まり続ける。ただし報告へは残す。失敗させないことと、見せないことは別である。

報告は `scan_report/` へ書き出し、継続的インテグレーションでは成果物として
30 日残す。リポジトリへは含めない。実行のたびに変わるものを追跡すると、
差分が読めなくなる。

### 検査器の版

検査器は commit ではなく image の digest で固定する。

```text
aquasec/trivy:0.72.0@sha256:cffe3f5161a47a6823fbd23d985795b3ed72a4c806da4c4df16266c02accdd6f
```

中身が後から変わると、同じ commit を検査しても結果が変わる。
更新は手作業とし、[外部の動作の参照](../maintainers/continuous_integration.md#外部の動作の参照)
と同じ扱いにする。

ホストの Docker の socket は渡さない。渡すと、検査器がホストの Docker を
操作できる。検査するだけなら、書き出した内容を読ませれば足りる。

## 5. 検査が働いていることの確認

検査は「指摘が出ないこと」だけを見ていると、
設定の誤りで何も検査していない状態に気づけない。

書式検査、セキュリティ検査ともに、対象ファイル数と実行結果を確認する。
設定を変更した際は、意図的に指摘が出る状態を作り、検出されることを確かめる。

イメージの検査は、指摘の残っているイメージを同じ条件へ通し、失敗することを
確かめる。検査の対象が空でも、指摘が出ないという結果は同じになる。

## 6. 一括検証

上記をすべて順に実行する。

```bash
docker compose exec web bin/verify
```

いずれかの手順が失敗した時点で終了し、終了状態は失敗になる。

実行する手順は `config/verify.rb` に定義する。
検証手順の定義はこの 1 か所だけとし、他の場所へ書き写さない。

| 手順                    | 内容                    |
| --------------------- | --------------------- |
| 準備: 依存とデータベース         | 依存の確認とデータベースの用意       |
| 書式: Ruby              | 書式検査                  |
| セキュリティ: 依存の脆弱性        | 依存ライブラリの監査            |
| セキュリティ: 静的解析          | アプリケーションコードの静的検査      |
| テスト: 全件（実ブラウザーを除く）    | 実ブラウザーを要する層を除くすべてのテスト |
| テスト: 初期データ            | 初期データの投入が成功すること       |

### 範囲を絞って実行する

引数で範囲を選べる。自動実行が、分けて同時に走らせるために使う。

```bash
docker compose exec web bin/verify checks   # 書式とセキュリティ
docker compose exec web bin/verify tests    # テスト
```

テストはさらに分けられる。分け方は `lib/tasks/test_files.rb` が、その場の
ファイルから作る。一覧を書き写すと、層を足したときに片方だけが古くなる。

```bash
docker compose exec -e TEST_SHARD=1/3 web bin/rails test:except_browser
```

知らない名前は受け付けずに終了する。受け付けると、綴りを誤ったときに
何も実行せずに成功として返る。

### 継続的インテグレーション

手順の一覧は作り直さず、`bin/verify` をそのまま呼び出している。
検証内容が 2 か所で管理されると、手元と自動実行で結果が食い違う。

走らせる場面で 2 つに分ける。変更を出すたびに走るもの（`verify.yml`）と、
`main` へ入ったあとに走るもの（`operations.yml`）である。何をどこで走らせるか
と、その組み立ての詳細は
[継続的インテグレーションの構成](../maintainers/continuous_integration.md) にある。

寄稿者が知る必要があるのは、まず手元で `bin/verify` を通すことである。
自動実行はこれに加えて、構成の分離、実測した木との対応、配布物の書き出し
といった、コンテナの中からは実行できない検査も走らせる。

### 実行する場面

変更を出す前に一度通す。自動実行も同じ手順を呼ぶため、手元で通れば
そこでも通る。

## 7. 読み込む量の検証

一覧が出す問い合わせの回数を固定する。

性能の退行は、問い合わせが並べる記録の数に比例して増える形で現れる。関連を
1 件ずつ引くと、数件の一覧では気づかず、1 ページに並べる件数だけ倍になる。

### 速さでは測らない

実行の速さで確かめると、実行環境の速さに左右されて間欠的に失敗する。
出した問い合わせの件数は環境によらない。

期待値へ絶対の件数も書かない。書くと、無関係な変更のたびに書き換えが要る。
記録を増やして 2 回数え、増えないことで確かめる。

補助は `test/test_helpers/query_count_test_helper.rb` に置く。
一覧ごとの確認は `test/controllers/list_query_count_test.rb` と、
一覧ごとのコントローラーのテストが持つ。

### 数え方で取りこぼすもの

いずれも「増えていない」という結果になるため、書いたままでは気づけない。

| 書き方                | 何が起きるか                          |
| ------------------ | ------------------------------- |
| 結び付ける記録を同じ相手にする    | 2 回目以降が問い合わせのキャッシュから返り、増えない     |
| 参照できない記録で数える       | 一覧が空のままで、関連を引かない                |
| 0 件との比較にする         | 並ぶ記録が無い一覧は関連を引かず、増えても増えないように見える |

対処として、結び付ける記録は 1 件ずつ別に作り、増やした記録が実際に並んで
いることを確かめてから件数を比べる。

### 応答の速さ

動かす機械によって変わるため、合否には使わない。報告として残す。

```bash
docker compose -f compose.production.yaml exec web \
  env LOAD_SAMPLE_SCALE=20 bin/rails officeweave:load_sample
```

```bash
BASE_URL=http://127.0.0.1:3210 \
LOAD_MEASUREMENT_EMAIL=measure@load-sample.invalid \
LOAD_MEASUREMENT_PASSWORD=... \
script/measure_load
```

測る前にデータを積む。空のデータベースへ要求を投げても、応答の速さは
分からない。積むのは専用の組織であり、既にある組織の記録には触れない。

測るのは、同時に要求が来たときに応答が返り続けるかである。
200 以外が混ざっていれば測定は成立しない。混ざったままの値は意味を持たない。

報告は `load_report/` へ書き出す。リポジトリへは含めない。
継続的インテグレーションでは、配布用の構成を起こしている仕事の中で測り、
成果物として 30 日残す。

起動している構成と積んだデータが前提になるため、一括検証へは入れない。

## 8. 実ブラウザーでの検証

`test/browser/` の層は、実際のブラウザーで操作が成立することを確かめる。

```bash
docker compose -f compose.yaml -f compose.browser.yaml up -d
```

```bash
docker compose -f compose.yaml -f compose.browser.yaml exec web bin/rails test:browser
```

既定のシステムテストは rack_test で実行する。HTML を解析するだけであり、
要素が重なって押せない、CSS の指定で見えない、ブラウザーが解釈しない入力欄の
指定、といった状態を検知しない。この層はそこを見る。

### ブラウザーの置き場所

ブラウザーは別の service として置く（`compose.browser.yaml`）。
開発用のイメージへは入れない。イメージの大きさと組み立て時間が増え、
検証の実行環境も利用者の環境から離れる。

版は image の digest で固定する。中身が後から変わると、同じ commit を検証しても
結果が変わる。更新は手作業とし、
[外部の動作の参照](../maintainers/continuous_integration.md#外部の動作の参照) と
同じ扱いにする。

### 一括検証から外している理由

`bin/verify` はこの層を外して実行する（`bin/rails test:except_browser`）。
追加の道具なしで手元で実行できる状態を保つ。

外した層は、継続的インテグレーションの独立した仕事「実ブラウザー」で必ず
実行する。外していることを黙って済ませない。
失敗した場合は、そのときの画面を成果物として 30 日残す。

### アクセシビリティの自動検査

`test/browser/accessibility_audit_test.rb` が、そこで定めた主要な画面を判定する。
判定する画面の一覧はそのテストが持つ。本書へ写すと、画面を 1 つ足すたびに
本書も直すことになる。

基準は WCAG 2.0 と 2.1 の A、AA とする（`wcag2a` `wcag2aa` `wcag21a` `wcag21aa`）。
既定のまま任せると、規則が増えたときに何を満たしているのか読めない。

判定は axe-core へ任せる。達成基準を自分で読み替えて書くと、規格の実装を持つ
ことになり、更新に追随できない。

実ブラウザーで実行する。色の対比、要素の見え方、名前の解決は、画面の中で
計算した結果でなければ判定できない。

#### 通ったことの意味

自動で判定できるのは基準の一部である。読み上げの順序、文言の分かりやすさ、
操作の順序が業務として自然かどうかは扱わない。
通ったことを「使える」の証明にはしない。

次を合否に含めている。

| 見るもの        | 理由                              |
| ----------- | ------------------------------- |
| 判定した規則が 1 つ以上ある | 判定そのものが動いていない状態でも「指摘なし」になる      |
| 判定できなかった規則が無い  | 判断を保留したまま通すと、通ったことの意味が薄れる |

判定した規則の数を見ているのは、この製品が配信するスクリプトの出所を自分だけに限って
おり、`script` 要素を差し込む形の読み込みが塞がれるためである。

構造そのもの（読み飛ばし用リンク、地標、言語の切り替えの説明）は
`test/system/accessibility_test.rb` が確かめる。判定に任せる範囲と、
この製品として決めた作りを分けている。

### 書くときに気をつけること

| 事象                          | 対処                          |
| --------------------------- | --------------------------- |
| 押した直後に別の画面へ移ると、指示が捨てられて元の画面に留まる | 移動を伴う操作のあとは、完了を待ってから次へ進む    |
| 表示する言語が実行環境で決まる             | ブラウザーへ渡す言語を固定する（`--lang=ja`） |
| 利用者ごとに表示する言語が異なる            | 日本語で表示される利用者だけを使う           |
| 説明のための `aria-label` で操作を選ぶ  | 利用者が読む表記で選ぶ                 |

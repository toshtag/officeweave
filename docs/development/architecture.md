# OfficeWeave アーキテクチャ原則

本書は OfficeWeave の設計契約である。
個別の実装判断は、本書の原則に反しない範囲で行う。
原則そのものを変更する場合は、変更理由を記録したうえで本書を更新する。

前提として、製品は特定のフレームワークより長く存続しうる。
したがって、業務上の意味を持つコードほど、特定技術への依存を薄く保つ。

ただし、この前提を根拠として、すべてのコードをフレームワーク非依存にする契約へ拡張しない。
適用範囲は次のとおりとする。

```text
フロントエンド:
  ブラウザー標準を優先し、
  業務規則を DOM、通信、UI フレームワークから分離する。

サーバー側:
  Rails の標準的な構造を利用できる。
  本書は、Rails または Active Record への依存を一律に禁止するものではない。
```

## 1. モジュラーモノリス

単一のアプリケーションとして構築し、その内部でドメイン境界を表現する。

- 境界は、配置場所と依存の向きによって示す
- 境界をまたぐ参照は、公開された入口に限定する
- 分割の必要が実際に生じるまで、実行単位は分けない

分散構成は、運用と障害調査の難度を上げる。
組織規模と機能量が現在の想定を超え、単一構成では成立しないと確認できるまで採用しない。

## 2. サーバー生成 HTML を既定とする

画面はサーバー側で HTML を生成して返すことを既定とする。

- 永続化される業務状態の正本はサーバー側に置く
- クライアント側に、サーバーと重複する業務状態の正本を持たせない
- 画面遷移はブラウザーの標準的な仕組みで行う

一時的な表示状態は、この原則の対象外とする。
次のような状態をクライアント側で保持することは禁止しない。

- メニューの開閉
- タブの選択
- 入力途中の表示状態
- フォーカス位置
- ドラッグ中の位置

ただし、これらをサーバー側の業務状態と重複する正本にしてはならない。

## 3. JavaScript なしでも基本操作が完了する

登録、更新、削除、検索、一覧の絞り込み、ページ送りは、
JavaScript が動作しない状態でも完了できる構造とする。

JavaScript は必須要件ではなく、操作性を高めるための追加とする。
追加した機能が失敗した場合でも、元の操作手段が残っていなければならない。

この原則は、単純さと堅牢さのために置く。
サーバー側だけで操作が閉じていれば、画面の状態管理の大半が不要になる。

## 4. ブラウザー標準を優先する

まず次の順で検討する。

1. HTML
2. CSS
3. ブラウザーの標準 API

上位で目的を達成できる場合、下位を採用しない。

標準機能だけでは不足する場合に限り、自作の小さなモジュールと、
単独で交換可能な小規模ライブラリを比較して選択する。
比較の観点は次のとおりとする。

- 実装量
- 仕様の複雑さ
- セキュリティ
- 保守負担
- テスト可能性
- 交換可能性
- ライセンス
- 継続的な保守状況

依存を減らすことと、自前実装を優先することは同義ではない。
仕様が複雑な領域、とくに正確さと安全性が要求される処理を、
依存を避けるためだけに自作してはならない。

フレームワーク固有の API は、上記のいずれでも解決できない場合にのみ使用し、
使用箇所は接続層へ閉じ込める。

## 5. 業務ロジックを UI から分離する

JavaScript が必要な場合、依存は次の一方向とする。

```text
UI アダプター
    ↓
アプリケーション処理
    ↓
純粋なドメインロジック
```

純粋なドメインロジックから、次を直接参照してはならない。

- `document`
- `window`
- DOM 要素
- HTTP 通信
- タイマー
- ローカルストレージ
- UI フレームワークの API

純粋なドメインロジックが実際に存在する場合は、
ブラウザーがなくても単体テストできる状態に保つ。

### 適用条件

この分離は、クライアント側に業務規則、または複数段階のユースケースが存在する場合に適用する。
DOM 操作だけで完了する単純な表示改善に、存在しないドメイン層やアプリケーション層を作らない。

- 責務が存在しない層を作らない
- 空のディレクトリや抽象クラスを先行作成しない
- 単一モジュールで明瞭に実装できる操作を、形式だけの多層構造へ分割しない

## 6. 必要な範囲で依存の向きを制御する

複雑または重要な業務規則は、可能な範囲で、
UI、外部サービス、通信処理から独立して検証できる状態に保つ。

外部サービスや交換可能な技術との境界では、
業務側が必要とする操作を定義し、接続側がそれを実装する。

- 差し替えの影響範囲は、接続部分に閉じる
- 外部仕様の都合が、業務規則の表現を歪めない状態を保つ

### この原則が要求しないもの

本原則は、次を標準構成として要求しない。
Rails および Active Record の標準的な構造は、そのまま使用してよい。

- Active Record モデルとは別の、永続化非依存モデル
- すべてのモデルに対する Repository のような抽象化
- すべての入出力に対する専用の転送オブジェクト
- 単純な作成・参照・更新・削除に対する変換層
- 将来の交換可能性だけを理由とした抽象化

### 抽象化を追加する条件

次のいずれかが実際に成立した場合にだけ、抽象化を導入する。

- 複数の実装を実際に交換する必要がある
- 外部サービスを隔離する必要がある
- 重要な業務規則を単独で検証する必要がある
- 既存の結合が、変更またはテストを明確に妨げている

「将来必要になるかもしれない」という理由だけでは抽象化しない。

## 7. 外部依存をアダプターへ隔離する

外部サービス、外部プロトコル、UI 技術との接続は、専用の接続層に閉じ込める。

- 外部の用語やデータ形式を、そのままドメインへ持ち込まない
- 接続層で、自製品の用語とデータ構造へ変換する
- 外部仕様の変更が、ドメインの構造を変えない状態を保つ

対象は、自製品の外部にあり、仕様と可用性を自分たちで統制できない依存とする。
アプリケーション自身のデータベース永続化を、
外部サービス接続と同じ理由だけで抽象化層へ包まない。

## 8. フレームワーク名をドメインへ持ち込まない

業務上の概念を表すモジュール名、クラス名、メソッド名、変数名、ドメイン用語へ、
実装技術の名称を持ち込まない。

一方、接続層、設定、運用コード、移行コード、統合テストでは、
実際に接続する技術、プロトコル、提供者を明確にするため、必要な技術名を使用してよい。
接続対象を隠した抽象名だけにすると、かえって責務が不明瞭になる場合がある。

ただし、次の 2 点は例外なく守る。

- 開発規約が禁じる比較対象の固有名詞は、接続層を含めて使用しない
- 実際に採用していない技術の名称を、将来用の抽象化へ先行して含めない

クライアント側コードを追加する場合は、少なくとも次の責務を分離する。

- 業務上の規則を表す、UI に依存しない処理
- ユースケースを進行する処理
- DOM、通信、ブラウザー API、フレームワークと接続する処理

依存は、接続処理から UI 非依存の処理へ向ける。

本書は、これらの物理的なディレクトリ名やファイル配置を確定しない。
最初にクライアント側コードを追加するタスクで、
生成済みアプリケーションの構造と対象機能を確認して決定する。

## 9. 素の CSS を使用する

CSS は標準機能の範囲で構成する。

- CSS カスタムプロパティで設計トークンを表現する
- カスケードレイヤーで優先順位を明示する
- 命名は、見た目ではなく役割を表す

CSS の物理的なファイル分割は、本書では確定しない。実際の構成は
`app/assets/stylesheets/` が持つ。責務が増えたときに、そこで分ける。

内容を伴わないファイルやディレクトリを、配置を先に確定する目的で作成しない。

## 10. 依存を足すときに確かめること

ライブラリを追加する場合は、次の 2 つを説明する。

```text
解決したい具体的な問題
標準の機能だけでは足りない理由
```

「将来必要になりそう」という理由だけでは追加しない。

実行時に載る依存と、影響範囲の大きい依存については、保守が続いているか
と、ライセンスがこの製品と両立するかも確かめる。取り込んだものは、その
版が同梱するものごと配布物へ入る。

## 現在採用しない技術

初期段階では、次を採用しない。

- 分散サービス構成
- 機能単位で独立デプロイする複数アプリケーションへの分割
- 単一ページアプリケーション
- API 専用バックエンドと、分離したフロントエンドリポジトリ
- クライアント側ルーター
- クライアント側の大域的な状態管理
- JavaScript のバンドラーと、画面表示のためのビルド工程
- TypeScript
- ユーティリティクラス中心の CSS フレームワーク
- CSS プリプロセッサー
- CSS-in-JS
- UI コンポーネントフレームワーク
- アプリケーション外部に配置する共有インメモリーデータストア
- 専用の全文検索エンジン
- メッセージブローカー
- コンテナオーケストレーション基盤
- 独自のプラグイン実行基盤

### 上記が禁止しないもの

- モジュラーモノリス内部での、機能単位のコード境界
  （不採用とするのは、機能単位で独立してデプロイする構成である）
- プロセス内の一時データとキャッシュ
- テスト用のインメモリ実装
- 言語標準のデータ構造
- 開発ツールの実行に必要な、画面表示以外のビルド工程

いずれも、必要性が実際の実装で確認された時点で、対象範囲を限定して再検討する。
採用する場合は、本書の「現在採用しない技術」から外し、判断理由を記録する。

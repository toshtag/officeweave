# OfficeWeave テスト方針

本書は、テストの層、実行方法、書き方の取り決めを定義する。

## 1. テストの層

| 層         | 置き場所               | 対象                        |
| --------- | ------------------ | ------------------------- |
| モデル       | `test/models/`     | 業務規則、検証、状態遷移              |
| コントローラー   | `test/controllers/` | 応答、権限、経路                  |
| 結合        | `test/integration/` | 複数の画面や操作にまたがる流れ           |
| システム      | `test/system/`     | 利用者の操作としての一連の流れ           |
| ヘルパー      | `test/helpers/`    | 表示用の変換処理                  |
| メール       | `test/mailers/`    | 送信内容                      |
| 起動時の設定    | `test/lib/`        | `lib/` に置く設定の正本            |

## 2. 実行方法

すべてコンテナ内で実行する。

```bash
docker compose exec web bin/rails test
```

システムテストを含めて実行する場合は次を使う。

```bash
docker compose exec web bin/rails test:all
```

特定のファイルだけを実行する場合は、経路を渡す。

```bash
docker compose exec web bin/rails test test/controllers/health_controller_test.rb
```

### 一時データベースを使う手作業の検証

通常の構成に対して `bin/rails db:drop` を実行しない。
複数のデータベースを持つため、環境単位で消える。一時的なデータベースだけを
消したつもりでも、同じ環境の他のデータベースまで巻き込む。

専用の Compose project と volume を作り、検証後はその project だけを
`down --volumes` で削除する。

```bash
docker compose --project-name officeweave_check --env-file /tmp/check.env up -d
docker compose --project-name officeweave_check --env-file /tmp/check.env down --volumes
```

## 3. システムテストの実行方法

システムテストはブラウザーを起動せず、`rack_test` で実行する。

JavaScript なしで基本操作が完了することを設計上の要件としているため、
ブラウザーを使わない経路がそのまま検証対象になる。
ブラウザーを実行環境へ同梱すると、イメージの大きさと起動時間が増え、
検証の実行環境も利用者の環境から離れる。

JavaScript を必要とする挙動が実際に現れた時点で、
その画面に限ってブラウザーを使う実行方法を追加する。
その場合も、既定の実行方法は `rack_test` のままとする。

## 4. 書き方

### テスト名

テスト名は日本語で、期待する結果を書く。

```ruby
test "依存先が正常なら ok を返す" do
```

「〜のテスト」「〜をテストする」とは書かない。何を確かめたのかが残らない。

### 検証する内容

- 実装の内部構造ではなく、外から観測できる結果を検証する
- 1 つのテストで 1 つの結果を確かめる
- 失敗したときに原因が特定できる粒度にする

### 外部の差し替えライブラリ

差し替えのためだけに依存を増やさない。
標準の機能で異常系を再現できる場合は、そちらを使う。

差し替えの範囲は最小にする。接続設定そのものを差し替えると、
テストを包むトランザクションが失われるなど、対象外の挙動まで変わる。

### トランザクションで囲む既定を外す場合

同時実行を確かめるテストは、別々の接続から実行する必要があるため、
テストをトランザクションで囲む既定を外す。この場合、作った記録は確定する。

途中で終わった実行が記録を残すと、次の実行は識別子の重複で失敗する。
以降はそのファイルの全件が別の理由で崩れ、最初の 1 件の理由が読めなくなる。

影響はそのファイルの中に収まらない。連番は fixture の読み込みのたびに
fixture の最大 id へ戻る。残った記録がその次の値を占めていると、無関係な
テストの採番が必ずそこへ当たり、主キーの衝突として現れる。

後片付けは `IsolatedOrganizationTestHelper` を使う。

```ruby
include IsolatedOrganizationTestHelper

self.use_transactional_tests = false

setup    { @organization = create_isolated_organization(name: "...", code: "...") }
teardown { discard_organization(@organization) }
```

- 作る前にも同じ掃除を通し、前の実行の残りを引き継がない
- 模型の破棄契約ではなく、参照の順に直接消す。
  破棄には記録を残す契約が入っており、1 件でも残ると組織を消せない
- 読み込み済みの関連を使わない。関連を読んだあとに増えた記録を取りこぼす
- 組織より先に配下を消す。逆順にすると、組織だけが消えて配下が孤立し、
  次の実行の掃除からも見えなくなる

### 別プロセスの起動を待つ場合

起動そのものを確かめるテストは、実際に別のプロセスを起動する。
既に起動しているテストプロセスの中で設定を読んでも、「起動しない」ことは
確かめられない。

待ち方は `BootProcessTestHelper` を使う。

```ruby
include BootProcessTestHelper

status, output = boot_process([ "bin/rails", "runner", script ], environment)
```

- 上限は行き詰まりを止めるためだけに置き、所要時間の判定には使わない。
  所要時間で受け取ると、実行環境の速さがそのまま結果に入る
- 退行は終了状態と出力で受け取る。起動しない場合はプロセスが異常終了する
  ため、上限へは達しない
- 上限に達した場合は、そこまでの出力を添えて失敗させる。
  待った秒数だけでは、起動しなかったのか遅かったのかを判別できない
- 停止させたあとは読み取り側の口を閉じる。子が残した書き手がいると、
  閉じるまで読み取りが終わらない

### 固定データ

固定データは `test/fixtures/` に置く。

- 実在する個人情報を書かない
- 実運用のデータを持ち込まない
- テストが読めなくなるほど大きくしない

## 5. 対象範囲の考え方

網羅率を目標にしない。次を優先して書く。

- 業務規則と権限の判定
- 状態遷移
- 境界値と異常系
- 一度壊れた箇所

自明な委譲や設定値の読み出しにテストを書かない。

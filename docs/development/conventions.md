# OfficeWeave 開発規約

本書は、命名と記述に関する取り決めを定義する。
実装、レビュー、ドキュメント作成のいずれもこれに従う。

## 1. プロジェクト識別子と製品表示名

| 用途           | 表記                                                   |
| ------------ | ---------------------------------------------------- |
| 技術識別子        | `officeweave`                                        |
| リポジトリ名       | `officeweave`                                        |
| ルートディレクトリ名   | `officeweave`                                        |
| コンテナイメージ名    | `officeweave`                                        |
| 製品表示名        | `OfficeWeave`                                        |
| 日本語での一般説明    | 組織向けコラボレーション基盤                                       |
| 英語での一般説明     | Self-hosted collaboration platform for organizations |

技術識別子には、ハイフン、アンダースコア、空白などの区切り記号を挿入しない。
大文字を含む表記は、利用者の目に触れる製品表示名としてのみ使用する。

## 2. ファイル名とディレクトリ名

命名規則が競合した場合、次の優先順位で適用する。

```text
1. 言語、フレームワーク、ツールが要求する標準名
2. 本書の言語別規則（Ruby、JavaScript、CSS、データベースの各節）
3. プロジェクト共通の既定規則
```

### 2.1 ツールが要求する標準名

`README.md`、`Gemfile`、`Dockerfile` のように、
エコシステム上の標準名、またはツールが読み取りに要求する名前は、その正式な表記を使用する。
共通規則へ合わせるための改名を行わない。

### 2.2 言語別規則

対象ファイルの言語について本書に規則がある場合は、その節の規則を適用する。
たとえば JavaScript のファイル名は、JavaScript の節で定める形式に従う。

### 2.3 プロジェクト共通の既定規則

上記のいずれにも該当せず、プロジェクトが独自に命名できるファイルとディレクトリには、
次を適用する。

- 英小文字、数字、アンダースコアを使用する
- 単語の区切りにはアンダースコアを使用する
- 日本語、空白、大文字を使用しない
- 名称は役割を表す

業務上の役割を表すファイルとディレクトリには、実装技術の名称を含めない。
接続層、設定、運用、移行、統合テストでは、
対象となる技術またはプロトコルを明確にするため、必要な技術名を使用してよい。

## 3. Ruby の命名

- クラスとモジュール: `CamelCase`
- メソッド、変数: `snake_case`
- 定数: `SCREAMING_SNAKE_CASE`
- 述語メソッドは `?` で終える
- 真偽値を返す変数名に `is_` を付けない

`!` は、同名の非 bang メソッドより危険、または強い振る舞いを持つ対のメソッドに使用する。

- レシーバー自身を変更する
- 失敗を戻り値で表す代わりに例外を送出する

例外を送出するという理由だけで、すべてのメソッドへ `!` を付けない。
対応する非 bang 版が存在しない場合は、`!` を付けず、
Ruby および採用フレームワークの一般的な慣習に従って判断する。

## 4. JavaScript の命名

- 関数、変数: `camelCase`
- クラス: `CamelCase`
- 定数: `SCREAMING_SNAKE_CASE`
- ファイル名: `kebab-case.js`
- 純粋なロジックを置く階層に、DOM やフレームワークを示す語を使用しない

## 5. CSS の命名

- クラス名は `kebab-case` とする
- 見た目ではなく役割を表す名称にする
- 設計トークンはカスタムプロパティとして `--` 接頭辞で定義する
- 要素の階層関係を、クラス名の連結で無制限に表現しない

## 6. データベースの命名

- テーブル名: 複数形の `snake_case`
- カラム名: `snake_case`
- 外部キー: `<関連名>_id`
- 真偽値カラム: 状態を表す形容詞または過去分詞
- 日時カラム: `_at` で終える
- 日付カラム: `_on` で終える
- 索引と制約には、対象が判別できる名称を付ける

### 6.1 カラム名

カラム名は、保持する値や属性の意味を自然に表す。
単数形へ機械的に変換しない。

件数、設定の集合、複数の値を意味する場合など、
複数形が自然な名称を禁止しない。

### 6.2 外部キー

参照先をそのまま表す関連では、モデル名に対応する名称を使用する。
同じ参照先が複数の役割を持つ場合や、自己参照の場合は、役割を表す関連名を使用する。

```text
user_id
creator_id
approver_id
parent_department_id
```

上記は命名形式の例であり、特定のモデル、テーブル、カラムの採用を決定するものではない。

### 6.3 索引と制約の名称

フレームワークまたはデータベースが生成する既定名で対象を判別できる場合は、
独自名へ変更することを必須としない。

名称の衝突、識別子の長さ制限、運用上固定すべき契約がある場合に限り、
明示的な名称を付ける。

## 7. 日本語コメント方針

プロジェクトが独自に記述するコードコメントは、日本語を基本とする。

以下は、日本語化だけを目的として変更しない。

- 言語やフレームワークのジェネレーターが生成したコメント
- 自動生成ファイル
- 外部ライブラリまたはベンダーコード
- ライセンス、著作権、法的通知
- 外部仕様から引用する必要がある識別子または定型文

生成されたコメントを変更する場合は、日本語化ではなく、
OfficeWeave 固有の判断や制約を記録する必要がある場合に限定する。

コメントは、コードを読めば分かることを繰り返さない。
次のいずれかを説明する必要がある場合にだけ記述する。

- なぜその制約が必要なのか
- なぜ単純な実装を採用できないのか
- 外部仕様との境界がどこにあるのか
- セキュリティ上の理由
- 将来壊してはいけない契約

## 8. 作業の進め方

- 1 タスクにつき 1 ブランチ 1 PR とし、独立して検証できる単位まで分解する
- ブランチ名は `<区分>/t<連番>-<短い英語>` とする。区分は作業のまとまりごとに決める
- ブランチ内のコミットは目的ごとに分ける
- 実装 → 対象テスト → Lint とセキュリティ検査 → 差分確認 → PR 作成の順に進める
- 検証がすべて成功した場合にのみ、merge commit 方式で `main` へマージする
- squash merge と rebase merge は使用しない。分割したコミットを履歴に残す
- マージ後は作業ブランチをリモートとローカルの両方から削除する
- 検証失敗、競合、未コミット変更がある状態ではマージしない

### タスクの分け方

- 1 タスクは、単独でテストまたは動作確認ができる単位までとする
- 画面、モデル、権限をまたぐ機能は、垂直に薄く通す形で 1 タスクにする
- 網羅性を目的とせず、前後の機能と接続された最小の実装で完了とする
- 先の予定として挙げただけの機能を、先行して実装しない

## 9. 記録の置き場所

進行と判断に関わる記録は、次の場所で役割を分ける。同じ内容を複数箇所へ写さない。

```text
今後の作業と不具合の内容        GitHub Issue
タスクをその順に並べた理由      PR の本文
完了時点で確かめたことの記録    PR の本文と、その実行結果
実装上の判断とその根拠          実装またはテストのコメント
機能の段階と到達度              docs/product/
自分の差分を見る観点            docs/development/self_review.md
想定規模での測定                docs/development/scale.md
製品の方向を決めた判断          docs/decisions/
版ごとの変更点                  CHANGELOG.md
実際の変更と検証の証跡          PR と Git の履歴
```

いずれも、その場に残り `git log` から辿れる。別の文書へ写すと、同じ内容を
2 か所で保つことになり、写した側は現在地を読み取れない分量へ育つ。

決定記録は 4 桁の連番を先頭に付ける。採用したあとは書き換えない。
判断を覆す場合は、新しい記録を足し、古い記録の状態をそこから指す。

## 10. 日本語コミット方針

コミットメッセージは日本語で記述する。

- 1 行目は種別接頭辞と要約とし、50 文字程度に収める
- 種別接頭辞は `feat` `fix` `docs` `refactor` `test` `chore` を使用する
- 2 行目は空行とする
- 3 行目以降に、変更理由と判断根拠を記述する
- 何を変更したかではなく、なぜ変更したかを本文に残す
- 1 コミットにはひとつの目的だけを含める

## 11. 日本語 PR 方針

PR のタイトルと本文は日本語で記述する。
本文には次の見出しを使用する。

```text
## 目的
## 変更内容
## 設計判断
## スコープ外
## 検証結果
## 次のタスク
```

依存を追加する PR では、アーキテクチャ原則が求める記録を本文へ含める。

## 12. 利用者向け文字列の多言語化方針

利用者の目に触れる文字列を、Ruby、ERB、JavaScript へ直接記述しない。
すべてロケールファイルを経由する。

```text
config/locales/
├── ja.yml
└── en.yml
```

- 初期の対応言語は日本語と英語とする
- 初期の既定言語は日本語とする
- 言語選択は利用者ごとの設定を持つ。決め方は第 15 節に定める
- 翻訳キーは、画面上の文言ではなく意味を表す名称とする
- 日本語のロケールファイルを正本とし、英語をそれに追随させる

## 13. 自然な英語用語を選ぶ手順

日本語の単語を機械的に直訳して命名してはならない。
新しいドメイン概念を追加する場合、実装前に次を定義し、レビュー対象とする。

```text
日本語表示名
英語の正式用語
意味
含むもの
含まないもの
近い既存概念との差
```

既に採用している用語は `app/models/` と `config/locales/ja.yml` が持つ。
新しい語がそれらと重ならないことを、まず確かめる。

名称の衝突は、次を対象に確認する。

- Ruby 標準ライブラリ
- 採用フレームワークの公開 API
- HTTP の用語
- データベースの予約語
- 同一プロジェクト内の既存ドメイン用語
- 利用者に表示する英語としての自然さ

衝突する場合は、既存の用語を流用せず、前掲の手順で新しい用語を定義する。

## 14. 外部固有名詞の扱い

比較対象となった外部企業、外部製品、外部の独自機能の名称を、
リポジトリの内部へ持ち込まない。対象は次を含む。

- ファイル名
- ディレクトリ名
- ソースコード
- コメント
- テスト名
- Fixture とサンプルデータ
- ドキュメント
- コミットメッセージ
- PR のタイトルと本文
- Issue
- リリースノート

機能や概念は、外部製品との比較ではなく、
OfficeWeave 自身の利用目的とドメイン用語によって定義する。

### 固有名詞の 3 分類

```text
禁止:
  比較対象として提示された外部企業、外部製品、独自機能の名称

使用可能:
  実際に採用する言語、フレームワーク、データベース、開発ツールの名称

必要な場合に使用可能:
  実際に実装する外部連携先、公開プロトコル、ストレージ方式などの名称
```

本規約が禁じるのは、製品比較のために持ち込まれる固有名詞である。
比較のための固有名詞と、実際の依存を識別するための技術名を混同しない。

ただし、禁止対象として明示された固有名詞は、
実際の連携用途であっても、個別に承認されるまで使用しない。

## 15. 表示言語の決定

表示言語は、要求ごとに次の順で決める。

```text
1. 利用者に設定された言語
2. 画面で選んだ言語（保持している場合）
3. ブラウザーが送る言語の希望
4. 既定の言語
```

対応していない言語が指定された場合は、次の候補へ落とす。

判定は `app/controllers/concerns/localizable.rb` の 1 か所に置く。
順序を変える場合は、本書とそこの両方を直す。

- 対応言語は `config.i18n.available_locales` で定義する
- 既定は日本語とする
- 言語の選択肢は、その言語自身の表記で並べる。翻訳すると、読めない言語で選ぶことになる
- 切り替えは JavaScript なしで完結する操作にする

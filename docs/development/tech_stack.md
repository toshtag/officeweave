# OfficeWeave 技術構成

本書は、採用する技術と版数の選定基準、対象系列、更新方針、および現在の候補を記録する。

候補は P1-T1 でそのまま採用し、動作を確認した。確定値は「7. 確定した版数」に記す。

## 1. 選定基準

技術と版数は、次の順で判断する。

1. 公式のサポートが継続していること
2. 対象環境（Linux および Apple Silicon を含む arm64）向けの配布物が存在すること
3. 導入時点で最新の安定版系列であること
4. セキュリティ修正が継続的に提供されていること
5. 依存関係が既存の採用技術と両立すること

「新しいから」という理由だけで採用しない。
「使い慣れているから」という理由だけで、サポートが終了した系列を採用しない。

| 対象           | 系列   | 候補         | 確認済みの入手方法                  |
| ------------ | ---- | ---------- | -------------------------- |
| Ruby         | 3.4  | `3.4.10`   | コンテナイメージ `ruby:3.4.10-slim-bookworm` |
| Ruby on Rails | 8.1  | `8.1.3`    | 公開ゲムリポジトリの最新安定版            |
| PostgreSQL   | 18   | `18.4`     | コンテナイメージ `postgres:18.4-bookworm` |

上記はいずれも、本書の作成時点で入手可能であることを実測して確認した。

```text
ruby:3.4.10-slim-bookworm     取得成功、ruby 3.4.10 [aarch64-linux] を確認
postgres:18.4-bookworm        取得成功
rails 8.1.3                   公開ゲムリポジトリの最新安定版として確認
```

確認は arm64 環境で行った。

### スキーマ定義の形式

スキーマ定義は SQL 形式（`db/structure.sql`）で保持する。

期間の重なりを除外する制約は Ruby 形式では表現できない。
取りこぼすと、複製した環境で重複を防げなくなる。

このため、アプリケーションのコンテナへはデータベースと同じ系列のクライアントを入れている。
版が異なると、スキーマ定義の書き出しが失敗する。他アーキテクチャ向けの配布物も同一タグで提供されている。

補助的に使用するもの。

| 対象             | 用途             | 方針                     |
| -------------- | -------------- | ---------------------- |
| Docker Compose | ローカルおよび配布用の実行環境 | 利用者の環境にある版を使用する        |
| Debian         | コンテナの基盤        | Ruby と PostgreSQL の公式イメージが採用する安定版に従う |

## 3. 更新方針

### パッチ更新

- セキュリティ修正を含むパッチ更新は、確認でき次第、単独のタスクとして適用する
- 適用時は、全検証が成功することを確認してからマージする

### マイナー更新

- 同一メジャー系列内の更新は、四半期に一度を目安に確認する
- 更新は単独のタスクとして扱い、機能追加と同じ変更に含めない

### メジャー更新

- メジャー更新は、独立したタスクとして計画する
- 変更点、非互換、移行手順を PR 本文へ記録する
- 実装の都合だけで判断せず、本書を先に更新する

### 版数の記載場所

版数は次の場所で管理し、いずれかを変更する場合は他方も同時に更新する。

- 本書の候補表
- 実行環境の定義ファイル（P1 以降で作成する）

同じ値を複数箇所へ書き写す必要が生じた場合は、
参照元をひとつに決め、他方はそれを読み取る形にする。

## 4. 採用する構成

```text
アプリケーション:
  Ruby
  Ruby on Rails
  PostgreSQL

画面:
  サーバー生成 HTML
  ERB
  素の CSS（カスタムプロパティ、カスケードレイヤー）

実行環境:
  Docker Compose

品質:
  Rails 標準のテスト機構
  Lint
  静的セキュリティ検査
  依存の脆弱性監査
```

画面表示のための Node.js ビルド工程は設けない。

## 5. 現時点で採用しないもの

| 対象               | 採用しない理由                            | 再検討の条件                       |
| ---------------- | ---------------------------------- | ---------------------------- |
| インメモリーデータストア     | セッションとキャッシュはデータベースで足りる             | 単一データベースで処理しきれない負荷が実測された場合   |
| 専用の全文検索エンジン      | データベースの全文検索機能で初期要件を満たせる            | 検索対象の規模または要件が、その機能で成立しなくなった場合 |
| メッセージブローカー       | 非同期処理はデータベースを介した仕組みで足りる            | 処理量または到達保証の要件が上回った場合         |
| コンテナオーケストレーション基盤 | 単一ホストでの運用を前提とする                    | 複数ホストでの可用性要件が生じた場合           |
| 単一ページアプリケーション    | サーバー生成 HTML で操作が完結する               | 該当しない（設計方針として不採用）            |
| 型付き JavaScript 言語 | ビルド工程が必要になり、画面表示の前提が変わる            | クライアント側コードが単体で保守困難になった場合     |
| CSS フレームワーク      | 素の CSS で構成を統制する                    | 該当しない（設計方針として不採用）            |

いずれも、必要性が実装で確認された時点で、対象範囲を限定して再検討する。

## 6. 依存を追加する手順

依存の追加は、[設計原則](../architecture/principles.md#10-依存追加には実証を求める)
の手順に従う。記録する項目と差し戻しの規則は、そちらを正本とする。

# OfficeWeave 技術構成

本書は、採用する技術と版数、選定の基準、更新の方針を記録する。

## 1. 選定基準

技術と版数は、次の順で判断する。

1. 公式のサポートが継続していること
2. 対象環境（Linux および Apple Silicon を含む arm64）向けの配布物が存在すること
3. 導入時点で最新の安定版系列であること
4. セキュリティ修正が継続的に提供されていること
5. 依存関係が既存の採用技術と両立すること

「新しいから」という理由だけで採用しない。
「使い慣れているから」という理由だけで、サポートが終了した系列を採用しない。

## 2. 採用している版

| 対象                 | 版        | 定義場所                                                                                                        |
| ------------------ | -------- | ----------------------------------------------------------------------------------------------------------- |
| Ruby               | `3.4.10` | `.ruby-version`、`Dockerfile` と `Dockerfile.production` の `RUBY_VERSION`                                       |
| Ruby on Rails      | `8.1.3`  | `Gemfile` と `Gemfile.lock`                                                                                    |
| PostgreSQL         | `18.4`   | `compose.yaml` と `compose.production.yaml` の `db` サービス。取り込むクライアントの系列は 2 つの `Dockerfile` の `POSTGRESQL_MAJOR_VERSION` |
| jwt                | `3.2.0`  | `Gemfile` と `Gemfile.lock`                                                                                    |
| selenium-webdriver | `4.46.0` | `Gemfile` と `Gemfile.lock`（試験のみ）                                                                             |

| Chromium           | `150.0`  | `compose.browser.yaml` の `browser` サービス（試験のみ）                                                               |

Ruby と PostgreSQL はコンテナイメージから取る（`ruby:3.4.10-slim-bookworm`、
`postgres:18.4-bookworm`）。いずれも arm64 向けの配布物があることを確認している。

補助的に使用するもの。

| 対象             | 用途             | 方針                     |
| -------------- | -------------- | ---------------------- |
| Docker Compose | ローカルおよび配布用の実行環境 | 利用者の環境にある版を使用する        |
| Debian         | コンテナの基盤        | Ruby と PostgreSQL の公式イメージが採用する安定版に従う |

### Ruby 4.0 を今は採らない理由

Ruby は 4.0 系が出ている（4.0.0 は 2025-12-25、現在 4.0.6）。4.0.6 の上で全検証が通ることを
確認したうえで、移らないことを選んだ。

理由は「移って得るものが無い」ことである。この製品が必要とする 4.0 の機能は
無く、3.4 系は通常のメンテナンスが続いている。危険を避けるためではない。

移らなかったきっかけは、配布するイメージの検査が止まったことである。
4.0.6 は default gem として json 2.18.0 を同梱しており、この版は
CVE-2026-33210（2026-03-19 公開）の対象として報告される。`ruby_4_0` の分岐は、
公開から 4 か月を経ても 2.18.0 のままである。

ただし、この製品が影響を受ける経路は無い。次の 2 つが独立して成り立つ。

```text
同梱された json は読み込まれない
  すべての実行経路が config/boot.rb を通り、Gemfile.lock の版が有効になる
  実測: bin/rails runner → 2.21.2 ／ bundler を通さない素の ruby → 同梱版

脆弱な経路を使っていない
  Advisory の対象は allow_duplicate_key: false を指定した解析だけである
  既定ではない。このリポジトリに指定は 1 件も無く、JSON.parse は
  すべて既定のオプションで呼んでいる
```

したがって、止まったのは「配布物に、報告の対象となる版が含まれる」という
事実に対してであり、この製品が危険であったからではない。

それでも移らないのは、次を天秤にかけた結果である。

| | |
| ----- | ------------------------------------------ |
| 得るもの  | 無い |
| 払うもの  | 検査に例外の仕組みを足す必要がある。導入先が自分で走査すると同じ報告が出て、各自が非該当を確かめ直すことになる |

得るものが無い以上、小さくても払う理由が無い。3.4 系が同梱するのは json 2.9.1
で、影響範囲の下限 2.14.0 を下回るため、留まることの費用も無い。

再検討の条件は 2 つあり、どちらか一方で足りる。

- 4.0 系が、報告の対象にならない json を同梱して出る
- 4.0 でなければできないことが、この製品に現れる

後者の場合、正しい対処は 3.4 に留まり続けることではなく、検査へ「確認済み、
非該当」を記録できる仕組みを足すことである。逃げ道の無い検査は、いずれ
迂回されるか無視される。`script/scan_container_image` は、データベースの
イメージについて同じ理由を自ら書いている。仕組みが無いことは
[#228](https://github.com/toshtag/OfficeWeave/issues/228) として登録した。

4.0 の非互換は確認済みであり、障害にならない。

### データベースのイメージに alpine を採らない理由

PostgreSQL の公式イメージには alpine 版もあり、同じ版数で配布されている
（`18.4-alpine`）。小さく、既知の脆弱性の指摘も少ない。それでも bookworm を使う。

alpine の C ライブラリ（musl）は locale を実装していない。名前としては受け取る
が、並びはバイト順になる。同じ 8 語を `ORDER BY` した実測結果である。

```text
bookworm(glibc)  apple | apricot | Banana | Cherry | あんない | サッカー | ざっし | 会議室
alpine(musl)     Banana | Cherry | apple | apricot | あんない | ざっし | サッカー | 会議室
```

この製品は利用者、部門、設備・備品、申請種別などを名前順で並べる。
乗り換えれば、その並びが変わる。

危険なのは、この違いが記録に現れないことである。どちらも `datcollate` は
`en_US.utf8`、`datlocprovider` は `c` と報告する。データベース自身の
照合順序の不一致の警告も出ない。

既にある導入先がデータディレクトリを引き継いだ場合、text 列の btree 索引は
作られたときの並びのまま残り、実際の比較と食い違う。`REINDEX` するまで、
検索と絞り込みが取りこぼす。

小ささと指摘の少なさは、これと釣り合わない。指摘の件数については、
データベースのイメージを合否に使わないと決めている（[品質基盤](quality.md)）。

再検討の条件は、照合順序を C ライブラリから切り離した場合とする。
PostgreSQL 18 は ICU と builtin の provider を持つ。そちらへ移すのであれば、
基盤の C ライブラリは判断の材料から外れる。ただしそれは、既にある
データベースの並びを変える作業であり、イメージの選択とは別に扱う。

### スキーマ定義の形式

スキーマ定義は SQL 形式（`db/structure.sql`）で保持する。

期間の重なりを除外する制約は Ruby 形式では表現できない。
取りこぼすと、複製した環境で重複を防げなくなる。

このため、アプリケーションのコンテナへはデータベースと同じ系列のクライアントを入れている。
版が異なると、スキーマ定義の書き出しが失敗する。

## 3. 更新方針

### パッチ更新

- セキュリティ修正を含むパッチ更新は、確認でき次第、単独のタスクとして適用する
- 適用時は、全検証が成功することを確認してからマージする

### マイナー更新

- 同一メジャー系列内の更新は、四半期に一度を目安に確認する
- 更新は単独のタスクとして扱い、機能追加と同じ変更に含めない

### メジャー更新

- メジャー更新は、独立したタスクとして計画する
- 変更点、非互換、移行手順を PR 本文へ記録する
- 実装の都合だけで判断せず、本書を先に更新する

### 版数の記載場所

版を決めるのは実行環境の定義ファイルであり、本書の表はその所在を示す。
どちらかを変更する場合は、両方を同時に更新する。

同じ値を複数箇所へ書き写す必要が生じた場合は、
参照元をひとつに決め、他方はそれを読み取る形にする。

依存を解決する道具の版は、この形で扱う。正本は `Gemfile.lock` の
`BUNDLED WITH` とし、`Dockerfile` と `Dockerfile.production` はそこから読む。
版を定義ファイルへ書き写すと、`Gemfile.lock` を上げたときに片方だけが古い
まま残り、組み立てたイメージが `Gemfile.lock` を書いたものと違う道具で依存を
解決する。この決め方は `test/configuration/bundler_version_test.rb` が確かめる。

### 読み取る形にできないもの

Ruby とデータベースの版は、この形にできない。`FROM` は組み立てが始まる前に
評価され、その時点でファイルを読めない。基盤のイメージを決める値は、
定義ファイルが直接持つしかない。

まとめきれない分は、食い違ったときに気づける形にする。
`test/configuration/runtime_version_test.rb` が次を確かめる。

| 確かめること                         | 食い違ったときに起きること              |
| ------------------------------ | --------------------------- |
| Ruby の版が定義ファイルで一致する            | 開発用と配布用が別の処理系で動く            |
| 構成ファイルが Ruby の版を書き直さない         | どちらが版を決めているのかが読めなくなる        |
| 開発用と配布用が同じデータベースのイメージを使う       | 手元で通ったものが配布先で通らない           |
| 取り込むクライアントの系列がデータベースの系列と一致する   | スキーマ定義の書き出しとバックアップの取得が失敗する  |

構成ファイルからは、組み立ての引数としての版の指定を外してある。
`Dockerfile` の既定と同じ値になるだけであり、渡す側と渡さない側が生まれると、
版を決めている場所が読めなくなる。

## 4. 採用する構成

```text
アプリケーション:
  Ruby
  Ruby on Rails
  PostgreSQL

画面:
  サーバー生成 HTML
  ERB
  素の CSS（カスタムプロパティ、カスケードレイヤー）

実行環境:
  Docker Compose

品質:
  Rails 標準のテスト機構
  Lint
  静的セキュリティ検査
  依存の脆弱性監査
```

画面表示のための Node.js ビルド工程は設けない。

## 5. 現時点で採用しないもの

| 対象               | 採用しない理由                            | 再検討の条件                       |
| ---------------- | ---------------------------------- | ---------------------------- |
| インメモリーデータストア     | セッションとキャッシュはデータベースで足りる             | 単一データベースで処理しきれない負荷が実測された場合   |
| 専用の全文検索エンジン      | データベースの全文検索機能で初期要件を満たせる            | 検索対象の規模または要件が、その機能で成立しなくなった場合 |
| メッセージブローカー       | 非同期処理はデータベースを介した仕組みで足りる            | 処理量または到達保証の要件が上回った場合         |
| コンテナオーケストレーション基盤 | 単一ホストでの運用を前提とする                    | 複数ホストでの可用性要件が生じた場合           |
| 単一ページアプリケーション    | サーバー生成 HTML で操作が完結する               | 該当しない（設計方針として不採用）            |
| 型付き JavaScript 言語 | ビルド工程が必要になり、画面表示の前提が変わる            | クライアント側コードが単体で保守困難になった場合     |
| CSS フレームワーク      | 素の CSS で構成を統制する                    | 該当しない（設計方針として不採用）            |

いずれも、必要性が実装で確認された時点で、対象範囲を限定して再検討する。

## 6. 依存を追加する手順

依存の追加は、[設計原則](architecture.md#10-依存追加には実証を求める)
の手順に従う。記録する項目と差し戻しの規則は、そちらを正本とする。

本書は、採用した技術と版数を記録する。追加してよいかどうかの判断は扱わない。

# OfficeWeave 設定

本書は、実行時に設定できる環境変数と、稼働確認の方法を定義する。

設定値は環境変数で与える。設定ファイルを書き換える運用にしない。
書き換えを前提にすると、アップグレードのたびに利用者側の変更が失われる。

## 1. 環境変数

雛形は [.env.example](../../.env.example) にある。
複製して `.env` として使用する。`.env` はリポジトリへ含めない。

### データベース接続

| 変数                   | 必須                | 既定値                       | 内容                     |
| -------------------- | ----------------- | ------------------------- | ---------------------- |
| `DATABASE_HOST`      | いいえ               | `localhost`（コンテナ構成では `db`） | 接続先のホスト名               |
| `DATABASE_PORT`      | いいえ               | `5432`                    | 接続先のポート                |
| `DATABASE_USER`      | いいえ               | `officeweave`             | 接続に使う利用者名              |
| `DATABASE_PASSWORD`  | 本番環境では必須          | なし                        | 接続に使うパスワード             |
| `DATABASE_NAME`      | いいえ               | 環境ごとの既定名                  | 接続先のデータベース名            |
| `TEST_DATABASE_NAME` | いいえ               | `officeweave_test`        | テスト用のデータベース名           |
| `RAILS_MAX_THREADS`  | いいえ               | `5`                       | 接続プールの上限               |

### 組織

| 変数                  | 必須  | 既定値           | 内容    |
| ------------------- | --- | ------------- | ----- |
| `ORGANIZATION_NAME` | いいえ | `OfficeWeave` | 組織の名称 |
| `ORGANIZATION_CODE` | いいえ | `default`     | 組織の識別子 |

### 初期利用者

`script/seed_initial_user` で最初の利用者を作成する際に使用する。
利用者が既に存在する場合は何も行わない。

これらの変数は web と worker の共通環境へは置かない。
`script/seed_initial_user` が、変数名だけを指定して一時コンテナへ渡す。
常駐するコンテナへ渡すと、初期管理者の平文パスワードがその寿命のあいだ
環境に残り、`.env` から消しても作成済みのコンテナからは消えない。

| 変数                      | 必須  | 既定値   | 内容                |
| ----------------------- | --- | ----- | ----------------- |
| `INITIAL_USER_NAME`     | いいえ | `管理者` | 表示名               |
| `INITIAL_USER_EMAIL`    | はい  | なし    | メールアドレス           |
| `INITIAL_USER_PASSWORD` | はい  | なし    | パスワード。15 文字以上とする  |

メールアドレスとパスワードのどちらかが未設定の場合、利用者は作成されない。
開発環境も同じとする。手順書に載る資格情報でそのまま使い始められる状態を作らない。

値は `.env` から読む。`--env-file` を指定した場合はそのファイルを使う。
同名のホスト環境変数は使わない。指定した設定ファイルが常に正本となる。

```bash
script/seed_initial_user --env-file /path/to/env
```

動的に作った値を使う場合も、環境変数へ export するのではなく、
所有者だけが読める一時ファイルを用意して渡す。

```bash
env_file="$(mktemp)"
chmod 600 "$env_file"
```

初期利用者の作成後は、`INITIAL_USER_PASSWORD` を `.env` から削除する。
web と worker には渡していないため、作り直しは要らない。

`bin/diagnose` が確かめるのは、Rails の実行環境へ渡っていないことである。
ホストの `.env` に値が残っているかどうかは分からない。そこはファイルを見て確かめる。

利用者が既に存在する場合、`script/seed_initial_user` は何も行わない。

### パスワードの要件

新しく設定するパスワードへ適用する。適用先は管理者画面での作成と変更、
`script/seed_initial_user` による初期利用者、CSV 取込で新しい利用者へ割り当てる内部用の値である。

```text
最低長      15 文字
数える単位   文字数（バイト数ではない）
文字種      混在を求めない。大文字・数字・記号は必須ではない
空白        含めてよい。ただし空白だけの値は使用できない
禁止する値   change_me、password、officeweave
```

多要素認証を持たない単一要素の認証であるため、長さだけを条件とする。
混在規則は覚えにくい短い値へ人を誘導し、長さの利点を打ち消す。

空白だけの値は長さとは別に拒む。Rails の `has_secure_password` は空文字でない
値なら digest を作るため、長さを満たした空白は必須の確認も長さの確認も通り抜ける。
タブと全角空白も同じ扱いとする。空白を含む通常の値は受理する。

禁止する値は、前後の空白と大文字小文字の違いを無視した完全一致で判定する。
無視する空白の範囲は、空白だけの値を拒む判定と同じとする。ASCII 空白のほか、
タブ、改行、全角空白、ノーブレークスペースも前後の空白として扱う。
`officeweave-is-not-the-password` のように部分として含むだけの値は拒まない。

保存済みのパスワードは自動では無効にしない。要件を満たさない値で既に運用している
利用者も、これまでどおりログインできる。氏名や権限などの更新でも、新しい
パスワードは求めない。設定し直す場合にだけ、要件を満たす値が必要になる。

### メール送信

`SMTP_ADDRESS` を設定すると送信を開始する。
未設定の場合、開発環境では `tmp/mails` へ書き出し、それ以外の環境では送信しない。
未設定のまま送信を試みると、待ち時間だけが増えて何も届かない。

| 変数                     | 必須            | 既定値                     | 内容                  |
| ---------------------- | ------------- | ----------------------- | ------------------- |
| `SMTP_ADDRESS`         | 送信する場合は必須     | なし                      | 送信サーバーのホスト名         |
| `SMTP_PORT`            | いいえ           | `587`                   | 送信サーバーのポート          |
| `SMTP_DOMAIN`          | いいえ           | なし                      | 送信時に名乗るドメイン         |
| `SMTP_USER_NAME`       | いいえ           | なし                      | 認証に使う利用者名           |
| `SMTP_PASSWORD`        | いいえ           | なし                      | 認証に使うパスワード          |
| `SMTP_AUTHENTICATION`  | いいえ           | なし                      | 認証方式                |
| `SMTP_ENABLE_STARTTLS` | いいえ           | `true`                  | 暗号化への切り替えを試みるか      |
| `MAIL_FROM`            | いいえ           | `officeweave@localhost` | 送信元のアドレス            |
| `APPLICATION_HOST`     | 外部へ公開する場合は必須  | 運用環境では `localhost`       | 利用者が接続するホスト名        |
| `APPLICATION_PROTOCOL` | いいえ           | `https`                 | メール本文の URL に使うプロトコル |
| `APPLICATION_PORT`     | いいえ           | なし                      | 公開 URL に明示するポート      |

`APPLICATION_HOST` の用途は 2 つある。メール本文の URL と、運用環境で受け入れる `Host` である。
詳細は [ホスト名の制限](#ホスト名の制限) を参照。

`APPLICATION_PORT` は `WEB_PORT` とは別物である。

```text
WEB_PORT          ホストから web コンテナへ公開するポート
APPLICATION_PORT  利用者が公開 URL から接続するポート
```

`APPLICATION_PORT` は、利用者が 80 または 443 以外のポートへ接続する場合に設定する。
逆プロキシの有無とは独立している。両者は一致する場合もあれば、異なる場合もある。

```text
逆プロキシが 443 を公開する:
  WEB_PORT=3210
  APPLICATION_PORT は未設定
  https://officeweave.example.com

逆プロキシが 8443 を公開する:
  WEB_PORT=3210
  APPLICATION_PORT=8443
  https://officeweave.example.com:8443

逆プロキシを使わず 3210 を直接公開する:
  WEB_PORT=3210
  APPLICATION_PORT=3210
  http://officeweave.example.com:3210
```

`WEB_PORT` から公開 URL のポートを自動で決めない。
逆プロキシやポート転送の背後では、内部のポートが利用者の接続先と一致せず、
自動で決めると内部のポートがメール本文へ混ざる。

値は 1 から 65535 までの整数だけを受け付ける。
未設定と空文字は「ポートを明示しない」として扱い、それ以外の値では起動しない。
先頭の 0 や前後の空白は補正せず、誤設定として扱う。

### 認証

| 変数                        | 必須  | 既定値        | 内容                                     |
| ------------------------- | --- | ---------- | -------------------------------------- |
| `AUTHENTICATION_PROVIDER` | いいえ | `internal` | 登録済みの認証方式の名前。未登録の値と空文字を指定すると起動に失敗する |

未設定と空欄は区別する。
変数そのものが無い場合は内部認証を使う。
`AUTHENTICATION_PROVIDER=` と書いた空欄は設定の誤りとして扱い、起動しない。
前後に空白を含む値も同じく起動しない。値は補正しない。

差し替えの手順は [認証方式の差し替え](authentication.md) を参照。

### 通信

| 変数          | 必須  | 既定値    | 内容                          |
| ----------- | --- | ------ | --------------------------- |
| `FORCE_SSL` | いいえ | `true` | 暗号化された通信を必須にするか（運用環境でのみ有効） |

逆プロキシで暗号化を終端する構成では、既定のままにする。
内部ネットワークだけで平文運用する場合に限り `false` にする。

`FORCE_SSL=true` の場合、セッション Cookie には `Secure` が付く。
`false` にした平文の構成では付かない。付けると Cookie が送られなくなる。

### ホスト名の制限

運用環境では、`APPLICATION_HOST` に指定した 1 つのホスト名だけを受け入れる。
異なる `Host` を持つ要求は 403 で拒否する。

```text
許可: APPLICATION_HOST と完全に一致するホスト名（ポートの有無は問わない）
拒否: それ以外のすべて（ループバックの IP を含む）
```

正規表現や任意のサブドメインは許可しない。
稼働確認の `/up` と `/health` も検査から外さない。
外すと、その経路だけは任意の `Host` で到達できる。

ループバックへ直接確かめるときは、`Host` ヘッダーを明示する。

```bash
curl -fsS -H "Host: ${APPLICATION_HOST}" http://127.0.0.1:3000/up
```

開発環境ではこの制限を適用しない。

#### 値の検査

値は起動の時点で検査する。不正な場合は web も worker も起動しない。

| 設定                              | 起動        |
| ------------------------------- | --------- |
| 未設定                             | `localhost` |
| ホスト名（`officeweave.example.com`） | そのホスト名    |
| IP アドレス（`192.0.2.10`）           | その IP     |
| 角括弧付きの IPv6（`[2001:db8::10]`）    | その IP     |
| 明示した空文字                         | 起動しない     |
| ゾーン識別子を含む IPv6（`[fe80::1%eth0]`） | 起動しない     |
| 前後に空白を含む値                       | 起動しない     |
| スキームを含む値                        | 起動しない     |
| 経路、クエリ、フラグメントを含む値               | 起動しない     |
| ポートを含む値                         | 起動しない     |
| ワイルドカードや複数ホスト                   | 起動しない     |

値は加工しない。前後の空白を取り除いて受理することはない。
誤設定を推測して直すと、設定に書いた値と実際に動く値が食い違う。

未設定と、`APPLICATION_HOST=` と書いた空欄は区別する。
空欄は誤設定として扱い、`localhost` へは落とさない。
これは `AUTHENTICATION_PROVIDER` と同じ契約である。

ポートは含めない。受け入れ側はポートの有無を問わずに照合するため、
`officeweave.example.com` と書けば `officeweave.example.com:3210` も受け入れる。
国際化ドメインは Punycode（`xn--` から始まる ASCII 表記）で指定する。

IPv6 は角括弧で囲んで指定する。ゾーン識別子は含めない。

```text
正: [2001:db8::10]
誤: [fe80::1%eth0]
```

ゾーン識別子は、その端末のネットワークインターフェースに依存する。
この値は稼働確認と利用者へ送る URL で共有するため、
サーバー側のインターフェース名を利用者へ配ることになる。

#### 公開先としての妥当性

書式が正しくても、利用者が接続できるとは限らない。
`bin/diagnose` の「メール本文の URL」は、運用環境で次を注意として扱う。

```text
localhost とその下位の名前（portal.localhost）
ループバックの IP（127.0.0.1、[::1]、[::ffff:127.0.0.1]）
接続先を特定しないアドレス（0.0.0.0、[::]）
```

いずれも設定としては正しいため、起動は拒否しない。
単一端末での試用や、逆プロキシを整える前の確認では、この値のまま動かせる必要がある。
問題になるのは、利用者へ送る URL としてだけである。

### セッション

ログイン状態は、次のどちらか一方でも超えると終わる。

| 期限    | 長さ     | 起点            |
| ----- | ------ | ------------- |
| 無操作期限 | 30 分   | 最後の認証済み要求     |
| 絶対期限  | 8 時間   | ログインしてセッションを作成した時刻 |

絶対期限は操作では延びない。延びると、使い続けている端末では期限が無いのと変わらない。
セッション Cookie の有効期限は、記録側の絶対期限と一致させる。
期限を過ぎたセッションは、記録と Cookie の両方を破棄する。

この 2 つの期限は現段階では設定で変更できない。
運用先ごとに変更する必要が確認された時点で判断する。

### ジョブの実行

| 変数                          | 必須  | 既定値                             | 内容                     |
| --------------------------- | --- | ------------------------------- | ---------------------- |
| `QUEUE_DATABASE_NAME`       | いいえ | `officeweave_development_queue` | 未処理のジョブを置くデータベース       |
| `QUEUE_DATABASE_CONNECTIONS`| いいえ | `5`                             | worker が張る接続の上限        |
| `JOB_THREADS`               | いいえ | `2`                             | 1 process が同時に実行するジョブ数 |
| `JOB_PROCESSES`             | いいえ | `1`                             | worker process の数      |

メールと Webhook の送信は、要求の外で行う。
送信の待ち時間で画面の操作が止まらないようにするためである。

ジョブは PostgreSQL へ保存する。web も worker も入れ替えて構わない。
未処理のジョブは残り、worker が起動した時点で処理される。

```text
db      業務データと未処理のジョブを、別のデータベースへ保持する
web     画面と API。ジョブを積む
worker  ジョブを実行する。ホストへポートを公開しない
```

`QUEUE_DATABASE_NAME` は、接続先のサービスは同じで論理データベースだけを分ける。
新しい PostgreSQL コンテナやホストの公開ポートは増やさない。

`JOB_THREADS` は `QUEUE_DATABASE_CONNECTIONS - 2` 以下にする。
worker は実行 thread のほかに、待機と heartbeat でも接続を使う。
不足すると、待機の側が接続を取れずに止まる。`bin/diagnose` が矛盾を検出する。

#### 実行の保証

実行は at-least-once とする。厳密に 1 回だけの実行は保証しない。

```text
- 送信サーバーが受理した直後に接続が切れると、同じメールが二度届くことがある
- Webhook も同様に、同じ出来事が二度届くことがある
```

Webhook には、やり直しても変わらない `X-OfficeWeave-Delivery-Id` を添える。
受け取る側は、この値で重複を判別できる。

#### やり直し

一時的な失敗は初回に加えて 4 回やり直す。合計 5 回まで実行する。

```text
1 回目の待ち: 5 秒
2 回目の待ち: 30 秒
3 回目の待ち: 2 分
4 回目の待ち: 5 分
```

やり直す失敗と、やり直さない失敗を分ける。

```text
やり直す      接続の失敗、時間切れ、一時的な TLS の失敗、SMTP の混雑
              HTTP 408 / 425 / 429 / 5xx

やり直さない  SMTP の認証失敗、恒久的な 5xx、宛先の書式不正
              Webhook 宛先の検査による拒否
              HTTP 3xx と恒久的な 4xx
```

やり直しを尽くした失敗は消さずに残す。`bin/jobs_status --failed` で確認する。

#### 状態の確認

```bash
docker compose exec web bin/jobs_status
```

```bash
docker compose exec web bin/jobs_status --failed
```

失敗したジョブは、やり直すか捨てるかを運用者が決める。手順は出力に示される。
一覧にはジョブの引数、メール本文、Webhook の送信内容、例外の全文を出さない。

### Webhook の送信先

| 変数                                       | 必須  | 既定値 | 内容                       |
| ---------------------------------------- | --- | --- | ------------------------ |
| `WEBHOOK_PRIVATE_DESTINATION_ALLOWLIST`  | いいえ | 空   | 内部宛先へ送信を許す origin の一覧    |

Webhook は既定で、組織の外にある宛先だけへ送信する。

```text
- 方式は http または https
- ポートは 80 番または 443 番
- https を推奨する
- 利用者名やパスワード、# 以降の指定を含む URL は使えない
- ループバック、私用アドレス、リンクローカル、マルチキャスト、
  文書例示や予約済みの範囲へは送信しない
- IPv4 との変換や 6to4 のように、IPv6 の中へ IPv4 を埋め込む範囲へも送信しない
- 廃止済みの site-local（fec0::/10）へも送信しない
```

送信しない範囲は、IANA の special-purpose address registry を基準に決めている。
外部から到達できない用途のものと、IPv4 を内包する形式のものを対象とする。
埋め込まれた IPv4 を取り出して判定し直す形は採らず、範囲ごと拒否する。

宛先の検査は保存時と送信時の両方で行う。
送信時は名前解決をやり直し、その結果の IP へ接続先を固定する。
保存後に名前解決の結果が内部のアドレスへ変わっても、送信の時点で拒否できる。

`http_proxy` などの環境変数は Webhook の送信に使わない。
proxy を経由すると、接続先を固定しても実際の宛先が proxy の判断で決まる。

3xx の応答は追跡しない。`Location` へは再接続せず、応答の状態だけを記録する。

応答は読み捨てる。記録に残すのは状態であり、ヘッダーも本文も使わない。

1 つの応答で受け取る量は、合計 64 KiB までとする。上限は本文だけでなく、
ステータス行とヘッダーを含めた受け取り全体に掛かる。

```text
状態を受け取った後で超えた   そこで読むのをやめる。状態は記録する。やり直さない
状態を受け取る前に超えた     送信の失敗として記録する。やり直さない
```

圧縮した応答は要求しない。`Accept-Encoding: identity` を送る。
宛先がこれを無視して圧縮を返しても、展開はしない。本文を使わないため
圧縮しても得るものがなく、展開は小さい応答から大きな確保を生むためである。

1 回の送信は、開始から終了までを 30 秒までとする。

```text
1 回の操作が止まった場合   開く 5 秒、書く 10 秒、読む 10 秒で切れる。やり直す
全体が 30 秒を超えた場合   そこで打ち切る。やり直さない
```

少しずつ返し続ける宛先は、1 回ごとの上限に掛からない。全体の期限はそれを抑える。
期限で切れた送信はやり直さない。やり直しても同じ結果になり、
同じ待ち時間を最大 5 回繰り返すことになるためである。

送信に失敗した場合、記録へ残すのは区分ごとに決めた文面だけとする。
宛先、解決した IP、ポート、経路、送信内容、署名は残さない。
例外の文面もそのまま残さない。接続の失敗や TLS の失敗の文面には宛先が入る。

#### 内部宛先を許可する

閉じたネットワーク内の宛先へ送る必要がある場合に限り、完全な origin を指定する。

```text
WEBHOOK_PRIVATE_DESTINATION_ALLOWLIST=http://hooks.internal.example,https://10.0.0.20
```

これは防御を弱める設定である。指定した origin へは、内部ネットワークであっても送信できる。

```text
- 完全な origin だけを指定できる（方式、ホスト名、ポート）
- 経路や条件を含む指定は使えない
- ワイルドカード（*.internal.example）は使えない
- CIDR（10.0.0.0/8）は使えない
```

書式が不正な場合、黙って無視せず Webhook の送信をすべて拒否する。
設定したら `bin/diagnose` で確認する。

許可した origin でも、URL の検査、名前解決、接続先の固定、
TLS 証明書の検証はそのまま行う。名前解決のすり替えへの対策は無効にならない。

### 署名に使う鍵

| 変数                | 必須       | 既定値 | 内容                    |
| ----------------- | -------- | --- | --------------------- |
| `SECRET_KEY_BASE` | 配布用では必須  | なし  | Cookie と署名付き値の署名に使う鍵 |

配布用の構成では、未設定または空欄で構成の解決に失敗し、起動しない。
開発環境とテスト環境では Rails が環境ごとの値を自動で用意するため、設定しない。

値は推測されない乱数とする。

```bash
docker compose exec web bin/rails secret
```

鍵を変えると、発行済みのセッション Cookie がすべて無効になる。
利用者はあらためてログインすることになる。保存済みのデータは失われない。

`bin/diagnose` の「署名に使う鍵」が、設定されているかどうかを知らせる。

### 実行環境

| 変数          | 必須  | 既定値           | 内容                                   |
| ----------- | --- | ------------- | ------------------------------------ |
| `RAILS_ENV` | いいえ | `development` | `development` / `test` / `production` |

### コンテナ構成で使う値

Compose の構成ファイルが参照する。
`WEB_PORT` だけは、開発環境のメール本文の URL を組み立てる際にも参照する。
公開しているポートと URL のポートがずれないようにするためである。

| 変数                        | 既定値         | 内容                         |
| ------------------------- | ----------- | -------------------------- |
| `WEB_BIND_ADDRESS`        | `127.0.0.1` | ホスト側で公開するアドレス              |
| `WEB_PORT`                | `3210`      | ホスト側で公開するアプリケーションのポート      |
| `DATABASE_PUBLISHED_PORT` | `55432`     | ホスト側で公開するデータベースのポート（任意の override 時のみ） |

いずれもホスト側の公開設定であり、コンテナ間の接続には影響しない。
アプリケーションはコンテナ内の 3000 番で待ち受け、`db:5432` へ接続する。

#### 公開アドレス

既定では loopback にだけ公開する。
別の端末から接続させる場合に限り、次を明示する。

```text
WEB_BIND_ADDRESS=0.0.0.0
```

暗号化された通信を終端する仕組みはリポジトリに含まれていない。
この設定のまま公開ネットワークへ置かない。

#### データベースの公開

通常の起動では、データベースをホストへ公開しない。
ホストのデータベースクライアントから直接つなぐ場合にだけ、追加の構成を重ねる。

```bash
docker compose -f compose.yaml -f compose.database.yaml up -d
```

`DATABASE_PUBLISHED_PORT` が使われるのは、この構成を重ねたときだけである。
公開先は `127.0.0.1` に固定してあり、変更できるのはポートだけとする。

### ホスト側のスクリプトで使う値

`script/` のスクリプトが、ホストの環境変数として読む。
コンテナへは渡らない。時刻起動から呼ぶ場合は、その行で指定する。

| 変数                       | 既定値 | 内容                                 |
| ------------------------ | --- | ---------------------------------- |
| `BACKUP_KEEP`            | なし  | 取得先へ残す書庫の数。指定した場合だけ、超えた分を古い側から消す   |
| `BACKUP_PASSPHRASE_FILE` | なし  | パスフレーズのファイル。指定した場合だけ書庫を暗号化し、復元時に復号する |
| `FORCE`                  | なし  | `1` のとき、復元と開発データベースの再作成で確認を求めない     |

`.env` へ書いても、これらの値はスクリプトへ渡らない。
`.env` を読むのは Compose であり、コンテナへ渡す値だけを解決する。
`.env.example` へ載せていないのも同じ理由による。

`BACKUP_KEEP` と `BACKUP_PASSPHRASE_FILE` に既定値は置かない。
指定しなければ、書庫は増え続け、暗号化もされない。
どちらの詳細も [バックアップと復元](../operations/backup.md) にある。

`BACKUP_PASSPHRASE_FILE` はパスフレーズそのものではなく、経路を受け取る。
値を環境変数へ置くと、そこから呼ぶ子プロセスすべてへ渡り、記録へも写り得る。
ファイルは、読める利用者を運用の担当者だけに限る。

### 秘密情報の扱い

- パスワードと鍵をリポジトリへ含めない
- `config/master.key` と `.env` は追跡対象から除外している
- `.env.example` の秘密情報は空欄とし、そのまま使える値を書かない
- 空欄のまま使わない。配布用の構成では、空欄の `DATABASE_PASSWORD` で
  構成の解決そのものが失敗する
- 設定に残った既知の初期値は `bin/diagnose` が注意として知らせる

## 2. 稼働確認

用途の異なる 2 つのエンドポイントを用意している。

| 経路        | 確認する内容                | 応答                          |
| --------- | --------------------- | --------------------------- |
| `/up`     | アプリケーションが例外なく起動できたか   | 起動していれば 200                 |
| `/health` | 依存先へ到達できているか          | 正常なら 200、到達できなければ 503       |

`/health` の応答は次の形式とする。

```json
{
  "status": "ok",
  "checks": { "database": "ok" },
  "checked_at": "2026-07-29T06:36:23Z"
}
```

- `status` は個々の確認結果をまとめた値
- `checks` は依存先ごとの結果
- 到達できない依存先がある場合、`status` と該当する `checks` の値が `error` になり、応答は 503 になる

どちらも認証を要求しない。監視側が資格情報を持たずに到達できる必要がある。

### 使い分け

- コンテナの再起動判定には `/up` を使う。依存先の一時的な不調で再起動させない
- 監視と通報には `/health` を使う。依存先の障害を検知できる

### 確認例

```bash
curl -s http://127.0.0.1:3210/health
```
